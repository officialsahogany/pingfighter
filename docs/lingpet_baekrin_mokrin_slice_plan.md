## 2. D1이 만드는 마찰점과 해소 방법 (전부 코드 확인)

### 2-1. 온이마루 유예 (D2의 직접 결과)

현재 게이트는 펫 id 화이트리스트 하나뿐이다 —
`lingpet_mount_state.gd:31` `MOUNT_SUPPORTED_PET_IDS := ["onimaru"]`. **장착 스킬을
조회하지 않는다**(보유 여부도, 슬롯 장착 여부도). 그래서 게이트를 스킬 기반으로 일반화하면 **온이마루는
`오니마루의안장`이 없어 탑승 기능을 잃는다**(현행 동작 회귀).

권고: 게이트를 `펫 id -> 안장 스킬 id` 맵으로 만들고, 스킬이 아직 없는 펫은
**명시적 유예 목록**에 두어 현행 동작을 유지한다. 유예는 코드에 이유와 만료
조건(해당 안장 스킬 랜딩)을 적고 씰로 봉인한다 — 조용한 예외는 금지.

```
MOUNT_SADDLE_SKILL_IDS := { "baekrin": "baekrin_saddle", "onimaru": "onimaru_saddle" }
MOUNT_UNGATED_LEGACY_PET_IDS := ["onimaru"]   # 오니마루의안장 랜딩 시 제거
```

### 2-2. 트리거 라벨이 "자동"으로 하드코딩되어 있다

`scripts/stages/common/lingpet_rail_card.gd:226-227`이 링펫 카드마다
`"trigger_type": "auto"` / `"trigger_label": "자동"`을 박아 넣는다(확인). 토글
스킬을 그대로 올리면 HUD가 **거짓 표기**를 한다. 카드 빌더에서 trigger를
스킬별로 파라미터화하고 `"토글"` 라벨을 추가한다. 보스 카드 쪽에는 이미
`trigger_type`을 인자로 받는 선례가 있다(`stage1_dalji_boss_skill_cooldown_state.gd:191`).

### 2-3. 공유 쿨다운 10초가 자유 토글과 충돌한다

`lingpet_egg_runtime.gd:131` `COMPANION_SKILL_SHARED_COOLDOWN_SECONDS := 10.0`,
발동 시 `start_shared_cooldown(...)`(:3155). 안장이 이 쿨다운을 소모하면
"자유롭게 타고 내림"이 성립하지 않고, 묵린변신의 쿨다운까지 잡아먹는다.

그런데 **"시작하지 않음"만으로는 부족하다.** `_apply_shared_cooldown_to_current`
(`lingpet_companion_skill_persistence.gd:252`)가 `state.cooldown = maxf(state.cooldown,
shared_cooldown)`을 **모든 슬롯 상태에 역으로 전파**한다(확인). 즉 묵린변신을 쓰면
안장 카드도 10초 쿨다운 상태가 된다.

permit 계약 (S2에 전부 포함):

- 공유 쿨다운을 **시작하지도, 전달받지도** 않는다
- 자동 무장 / trigger count / launch feedback에서 제외
- 스냅샷에 **`activation_model`** 과 **`interaction_active` / `interaction_available`** 투영
- 레일은 **라벨뿐 아니라 progress / status / cooldown / tooltip 전체**를 permit 전용 분기로

> ⚠️ 라벨만 `"토글"`로 바꾸면 여전히 거짓 카드다. `lingpet_rail_card.gd:217`이
> `duration = maxf(1.0, ...)`으로 **최소 1초 쿨다운을 강제**하고 거기서
> `progress = 1 - remaining/duration` 충전 진행도와 `status`(charging/ready/casting)를
> 만들며, `:316` 툴팁은 `cooldown_seconds`가 0 이하면 기본값으로 되돌려 **쿨타임
> 문구를 반드시 출력**한다(확인). permit은 진행도 막대도, 쿨타임 줄도 없어야 한다.

분류는 스킬 메타데이터의 새 필드로 선언한다(암묵 분기 금지).

### 2-4. 탑승 런타임 소유권은 스킬 호스트로 옮기지 않는다

**D1은 슬롯 경제만 뒤집었지 런타임 소유권까지 뒤집지 않았다.** idle 게이트는
`lingpet_companion_skill_controller.gd:95`의 **슬롯 루프 안에서만** 적용되고
(`can_skip_idle` → `continue`로 그 슬롯의 스킬 업데이트만 건너뜀), 실제 탑승은
그 바깥 `_update_companion_motion`(`lingpet_egg_runtime.gd:2824`)에서 **항상**
갱신된다(확인). 따라서 탑승 생존 술어를 `needs_runtime_update_for_skill()`에
등재할 이유가 없다 — 넣으면 소유권만 흐려진다.

확정 계약:

- `baekrin_saddle` = 액티브 슬롯을 점유하는 **`interaction_permit`**
- **현재 액티브 슬롯에 장착된 라이브 permit이 있을 때만** 탑승 허용
- 자동 무장 / launch / skill-host update 대상에서 **명시적으로 제외**
- 탑승 상태와 전이 정리는 계속 `lingpet_mount_state`가 **단독 소유**
- egg runtime이 장착 id와 온이마루 유예를 해석해 **`mount_permitted` 하나만** 전달
- `needs_runtime_update_for_skill()`에는 탑승을 **넣지 않는다**

> ⚠️ **"해금"의 정의 = 현재 액티브 슬롯에 장착.** 단순 획득/보유가 아니다.
> 보유만으로 성립하면 슬롯 예산이 무의미해지고, 슬롯을 다른 스킬로 바꿔도
> 탑승이 남는다. §2-1의 맵도 "보유"가 아니라 **장착 슬롯 조회**로 구현한다.

**permit 철회 전이 (진입 게이트가 아니다).** "현재 장착된 permit만 유효"라면, 탑승
중에 안장 슬롯이 제거·교체되어 `mount_permitted`가 false가 된 **그 프레임에 강제
하차**해야 한다. 이건 새 패턴이 아니라 기존 계약 그대로다 — `advance()`는 이미
미지원 펫 / 컴패니언 비활성을 **진입 게이트가 아니라 기존 탑승의 철회 전이**로
처리한다(`lingpet_mount_state.gd:126` 부근: `if not MOUNT_SUPPORTED_PET_IDS.has(_pet_id)
or not companion_active:` → 탑승 중이면 `_dismount()` + `toggled=true`, 입력 엣지
처리보다 **먼저** 반환, 확인).

따라서 `mount_permitted`는 **`advance()`의 인자로 넘겨 같은 철회 조건에 합류**시키고,
처리 소유권은 egg runtime이 아니라 **`lingpet_mount_state`**가 갖는다. egg runtime은
장착 슬롯을 조회해 불리언 하나를 만들어 넘기는 역할만 한다.

씰 계약: **실제 슬롯 조회 → `_update_companion_motion()` → 같은 프레임 `mounted=false`**,
그리고 **슬롯을 유지한 대조군은 계속 탑승**. (대조군이 없으면 "항상 하차"와 구별 불가)

별건 문서 결함(이 슬라이스와 무관하지만 S0에서 같이 고친다): `CLAUDE.md` 트랩
스텁과 `docs/godot_runtime_traps.md`가 게이트 생존 소스를 `is_launch_blocked`라고
적었으나, shipped 코드 주석이 그 재사용을 **명시적으로 금지**하고
`needs_runtime_update_for_skill()`을 지정한다. 문서를 따라 등재하는 다른 스킬이
조용히 죽는다.

### 2-5. 슬롯 예산과 module 충돌

`lingpet_active_skill_slot_resolver.gd:52-69`(확인): 2번째 슬롯은
`is_second_active_unlocked()`(수호령강화 보상) **AND** `get_active_slot_count() >= 2`
**AND** 2번째 skill id 비어있지 않음 — 3중 조건. 게다가 두 스킬이 같은 모듈을
공유하면 `_would_share_module`로 슬롯이 **조용히 2→1로 붕괴**한다.

D1이 "해금되어야 탑승"이므로 이 진행 게이트는 오히려 의도에 부합한다. 다만
부화 직후에는 안장·묵린변신 중 하나만 장착 가능하다는 점을 기획에 반영해야
하고, 두 스킬의 `runtime_kind`가 겹치지 않도록 설계해야 한다.

## 3. D3(탑다운)이 만드는 에셋 / 렌더 결과

현행 `companion_carry`는 **정면 직립 이족 목말 25f** (`onimaru_companion_carry_idle_25f`)
이고, 애니메이터가 그 규격(25f 5×5)을 전제로 지오메트리를 재사용한다. 탑다운은
규격이 다르므로 **신규 렌더 분기가 선행**한다 — 탑다운 스틸을 기존 carry 슬롯에
넣을 자리가 없다.

| 에셋 | 상태 | 작업 |
|---|---|---|
| `백린_변신전`, `묵린` (정면 3/4) | ⭕ 즉시 | 누끼 → `cutin_art` / `concept_art_path` |
| `백린_빈안장_topdown` | 🔶 | 누끼 → 탑승 **M-베이스**. 탑다운 렌더 분기 선행 |
| `백린/묵린 위보는모습` (무안장 탑다운) | 🔶 | 비탑승 탑다운 베이스 |
| `백린_탑승` / `목린_탑승` | ❌ 직접 사용 불가 | 제3의 라이더가 베이크됨(플레이어블 5인 불일치) + M×N 조합 = 소켓 계약 위반. **탑다운 라이더 포즈 규격 참조**로만 |
| 캐릭터별 탑다운 착석 라이더 ×5 | ❌ 전무 | **N-세트 신규 제작** |
| `백린_목린_변신_18프레임` | ❌ **재생성**(D13 개정) | 첫 12프레임은 **상단 1536×768의 6×2**(셀 256×384)이며 **12프레임 전부 가장자리 접촉 0 = 잘린 곳 없음**. 불합격 사유는 **f6→f7 알파 중심 X +22.56px 점프**(운영 92px에서 약 5.4px 팝). ⚠️ 이전에 적은 "행3 꼬리 소실 / 비균일 그리드 / 스케일락 위반"은 **전부 철회**(6×3 오슬라이스 산물). per-frame rect 맵은 런타임 계약을 늘리므로 비권장 |
| `companion_walk` / `strike` / `cast` | ❌ 전무 | AutoSprite 뒷모습. **라비 선례처럼 1장 재사용 가능**(walk/strike/cast 동일 파일) |
| `cutin_anim` 32f / `dismiss` / `click_reaction` | ❌ 전무 | dismiss는 click_reaction 재사용 가능(라비 선례) |
| 스킬카드 ×2 | ❌ 전무 | **없으면 프리웜 스모크 즉시 RED** |
| 알 3키 | ⭕ | 공용 재사용 = 무비용 |

절약 **후보**(확정 아님): 묵린은 백린과 실루엣 IoU 0.9967이라 시트를 백린만 만들고
5초 변신을 리컬러로 처리할 수 있어 보인다.

> ⚠️ 앞서 근거로 든 `onimaru_*_amber`는 **런타임 리컬러 선례가 아니다 — 철회한다.**
> 온이마루는 amber를 **별도 PNG로 카탈로그에 연결**하고(`lingpet_catalog.gd:965`
> 부근, cutin / dismiss / click만 `_amber` 변형이며 컴패니언 시트는 아니다),
> 컴패니언 렌더러의 modulate는 `Color(1,1,1,alpha)`로 **RGB는 흰색·알파만**
> 적용한다(`lingpet_companion_renderer.gd:158`, 확인). 즉 현재 렌더 경로에는 색을
> 바꿀 수단 자체가 없다.

이 절약안은 아래 셋 중 하나가 검증돼야 확정된다:
1. 별도 리컬러 시트(가장 단순, 제작량 절반 절감은 사라짐)
2. 부위 마스크 기반 팔레트 셰이더(금색 장식 / 눈 / 안장 보존)
3. 단순 tint로 금색 장식·눈·안장이 훼손되지 않는다는 **픽셀 증거**

미결: 온이마루 carry를 탑다운으로 재제작할지(§5-6).

| 지점 | 함수 | 누락 시 증상 |
|---|---|---|
| `:80` | `reset(owner, registry)` | 전체 리셋에서 누락 → 상태 영구 잔존 |
| `:115` | `clear_for_tests(...)` | 씰 간 상태 오염 |
| `:146` | `reset_round(...)` | **라운드 경계 영구 누출** |
| `:173` | `update(...)` 의 `match get_skill_kind(...)` fanout | **아예 안 돌아감**(조용한 무동작) |

여기에 더해 **get/peek, draw, visibility / liveness, prewarm**까지 포함한 전수표를

> ⚠️ **형태가 하나가 아니다.** `update` / `get` / `peek`은 `match get_skill_kind(...)`
> 이지만 `reset` / `reset_round` / `draw`는 **명시적 호출 목록**이고 visibility는
> **혼합형**이다. `match`만 grep하면 **리셋·그리기 목록을 통째로 빠뜨린다** —
> 각 형태를 따로 훑어야 한다.

12조합 전부 구조적으로 정확히 0"은 **닫힌 증명이 아니다**:
- `target_x`는 **목표일 뿐 중앙 접촉 보장이 아니다** — 자동조종은
  `move_toward(player_pos.x, target_x, max_speed * fps_scale)`로 **프레임당 최대
  24px**만 이동한다(`active_item_aipill_behavior.gd:20-25`).
- 타구 배율은 고정값이 아니라 **랜덤 기본 배율 × 속도 감쇠 × 위치별 보정의 합성**
  이다(`paddle_bounce_speed_multiplier_resolver.gd:33` `get_scaled_random_multiplier`
  → `apply_dampened_multiplier` → `_apply_edge_hit_multiplier`).
- 제시했던 부등식 `mult < 1 + 0.5/cap`은 **정책 적용 직전 속도가 이미 현재 캡과
  같다**는 가정을 숨기고 있다. 실제 생존 조건은 **정책 직전 유효속도**까지 포함해야 한다.

⇒ 따라서 P0 채택(D6)의 근거는 "수학적으로 0임이 증명됨"이 아니라
**"관측 구간에서 이득이 식별되지 않았고, 리포 선례상 접촉 공속 배율 3종이 전부
캡 우회와 세트라 캡 준수 배율은 전례가 없다"** 이다.

⚠️ **"창 내 무실점"도 보증이 아니다.** 시뮬의 창 내 실점 0.000을
"`|vx| ≤ 26·cos25° ≈ 23.6 < 자동조종 24`이므로 항등적으로 무실점"이라고 쓰면
과잉이다 — 그 부등식은 **추적 오차가 늘지 않는다**는 조건에 가깝고, 초기 위치 오차·
남은 비행시간·패들 허용폭 없이는 캐치를 보장하지 않는다. 정확한 표기는
**"이 모델·이 시드 집합에서 0건"** 이다. 라이브 문구로 "5초 무실점"을 쓰지 말 것.

승격 금지 / 미확정:
- ⚠️ **P3(캡 해제)의 `+4.1577 Δnet/min`은 라이브 효과로 승격 금지.** 시뮬이 보스
  대쉬를 미모델인데, 실제 대쉬는 **일반 이동으로 못 닿을 때만** 발동하고
  (`_try_start_boss_dash`: `frames_to_contact = vertical_gap / (|vel.y|*boost)`,
  `if required_distance <= effective_speed * frames_to_contact: return false`),
  `frames_to_contact`는 공속에 반비례한다. 즉 **P3가 만드는 조건이 곧 대쉬 발동
  조건**이라 구조적 상향 편향이다. 발동률 0.30 / 리미트 0.60 / 신화 1.0,
  토큰 1 / 2 / 신화 S5 3개(+연쇄).
- ⚠️ **P0 vs P2 동등, P1 열세는 통계적으로 미확정.** P2−P0가 15초 +0.0060,
  55초 −0.0027로 **부호가 뒤집힌다**. 시드별 paired difference 분산·신뢰구간이
  없다. 현 표본으로는 "구분 불가"가 정확한 표현이다.

### 대쉬 경계 재실행 프로토콜 (P3 판정용, 착수 전 필독)

- **DiD 필수**: `P0/dashOFF`, `P0/dashON`, `P3/dashOFF`, `P3/dashON` 4칸을 **같은
  시드**로 돌리고 핵심값은 **(P3_ON − P3_OFF) − (P0_ON − P0_OFF)**.
  P3 ON−OFF만 보면 일반 대쉬 이득과 P3 특화 구제량이 섞인다.
- **실제 경로 관통 필수**: 수동 대쉬 근사 금지. `BossAiState.update()`
  (`scripts/ai/boss_ai_state.gd:626`의 `_try_start_boss_dash` 분기)를 관통해야 한다.
  ⚠️ 현재 시뮬은 `BossAiPredictionState` + `BossAiTurnInertiaResolver`만 조립해 쓰므로
  **보스 이동 루프를 실제 `update(delta, boss_pos, boss_vel, context)`로 교체**하는
  작업이 선행한다(작은 패치가 아니다).
- ⚠️ **BossAiState는 포인트 단위 무상태가 아니다.** 토큰·충전 타이머·대쉬/스턴·
  서브페인트·예측 상태가 전부 **인스턴스 변수**다(`boss_dash_tokens`,
  `boss_dash_charge_timer_frames`, `boss_dash_recharge_frames`,
  `boss_dash_stun_*`, …). 포인트마다 AI를 새로 만들면 토큰과 충전이 매번
  초기화되어 **대쉬가 과다 공급**된다. 따라서:
  - 단일 포인트 DiD라면 **"첫 포인트 경계 실험"으로 한정**해 보고한다.
  - Δnet/min까지 재평가하려면 **세션 시드당 AI 인스턴스 1개를 유지**한다.
  - **1.5초 재서브 구간도 `waiting_for_serve=true`로 실제 업데이트**해 충전 시간을
    진행시켜야 한다(안 그러면 토큰이 공짜로 찬다).
  - 이 경우 **기존 포인트 캐시는 폐기**한다(AI 상태까지 키에 넣는 것은 비현실적).
    ⇒ 1차 실행의 38분은 캐시 덕분이었으므로, 대쉬 재실행은 **경계 실험 범위로
    좁혀야** 한다(전체 쿨다운 스윕을 캐시 없이 돌리지 말 것).
- **함께 출력**: 대쉬 적격 프레임 수, 발동 수, 연쇄, 토큰 소비, 캐치 전환.
  ⚠️ **적격 여부는 외부에서 관측 불가**다 — `get_dash_token_snapshot()`은
  tokens / max_tokens / charge_timer / recharge_frames / charge_progress /
  available_timer / recovery만 노출하고 **적격 플래그가 없다**. 외부에서 게이트
  조건을 복사하면 "수동 근사 금지"와 충돌하므로, **실제 게이트 내부에
  행동 중립 테스트 프로브**를 심어 eligible / start / chain을 기록한다.
  ⚠️ 그 스냅샷 Dictionary는 **프레임당 재사용되는 공유 참조**다(코드 주석 명시).
  프레임을 넘겨 저장하려면 반드시 복사할 것.
  ⚠️ 단순히 "대쉬 후 캐치"를 세면 **인과적 전환이 아니다**. paired 반사실로

- **컨텍스트는 운영 순서를 따른다**: 손조립이 아니라
  `build_boss_ai_context(owner, registry)` → `ai_state.update(delta, ...)`

  ⚠️ **round-state 픽스처가 없으면 빌더가 `waiting_for_serve=true`로 폴백**하고
