# 승리 하이라이트 리플레이 — Codex 핸드오프 (1차 슬라이스)

작성 2026-08-07. 설계 확정 = 사용자 리뷰 2회 반영본.
구현 소유 = Codex. 이 문서가 계약 정본이며, 여기 없는 확장은 2차 슬라이스다.

---

## 0. 목적 / 범위

스테이지 클리어(플레이어 매치 승리) 시, 보스 상자 드랍 **직전**에 그 매치에서
가장 극적인 득점 장면 1~3개를 짧게 재생한다. 클릭/키 1회로 전체 스킵.

```
최종 득점 → 스코어보드(파워로스 진동) → [하이라이트] → 전리품(보스 슬럼프+상자) → 결과화면
                                          ^^^^^^^^^^ 신규
```

**1차 슬라이스 범위**: 플레이어 · 보스 · 공 · 궤적 · 표식.
**2차로 미룸**: 스킬 투사체, 스테이지 기믹, 히트스톱, 카메라 셰이크, 링펫.

### 0.1 기각된 접근 — 원본 화면 캡처

`get_viewport().get_texture().get_image()` 링버퍼는 채택하지 않는다.

- 전투 진입 후 출하 기본값은 Stable Monitor(144Hz 모니터 → 렌더 72 / 물리 72).
  [battle_view_layout.gd:30](../godot/scripts/core/battle_view_layout.gd#L30)의
  `RENDER_FPS_CAP_STABLE_PREFERRED_MAX := 72`가
  [project.godot:16](../godot/project.godot#L16)의 부트 캡 48을 런타임에 덮는다.
- 760×750 RGBA8 = 2.28MB/frame → 1.5초 클립 ≈ **246MB**, 3개면 약 738MB.
- 매 프레임 GPU→CPU 리드백은 파이프라인 스톨. 이 레포는 물리 캐치업 리드로우
  스파이럴 기왕력이 있다.

"불가능"이 아니라 **현재 예산에서 비추천**이며, 대신 아래 스냅샷 리플레이를 쓴다.

## 1. 삽입 지점 — 신규 래더 슬롯을 만들지 말 것

승리 래더는 **두 벌**이 존재한다.

- 정규: [battle_scene_match_flow_driver.gd:143](../godot/scripts/core/battle_scene_match_flow_driver.gd#L143)
- 폴백: [match_scoreboard_flow_controller.gd:15](../godot/scripts/core/match_scoreboard_flow_controller.gd#L15)

⚠️ **로직은 한 벌이지만 교체 지점은 2곳이다.** `_try_start_victory_loot_phase`는
함수로 한 번 정의되지만 호출 지점이 둘이다.

- 정규 래더는 `_apply_scoreboard_update_result`에서 **직접 호출**한다
  ([:143](../godot/scripts/core/battle_scene_match_flow_driver.gd#L143)) —
  콜백을 경유하지 않는다.
- 폴백 래더만 `try_start_victory_loot` 콜백 바인딩
  ([:94](../godot/scripts/core/battle_scene_match_flow_driver.gd#L94))을 쓴다.

따라서 `_try_start_victory_presentation` 구현은 **하나로 유지**하되,
**정규 직접 호출과 폴백 바인딩 양쪽을 모두 교체**해야 한다. 한쪽만 바꾸면 그 경로의
승리에서만 하이라이트가 조용히 건너뛰어진다. "단일 인터셉트"가 아니다.

```gdscript
# driver 내부. 콜백 키는 try_start_victory_presentation 으로 개명(폴백 래더 1줄 동반).
func _try_start_victory_presentation(registry, owner, reset_game_callback) -> bool:
    if _try_start_victory_highlight(registry, owner, reset_game_callback):
        return true                 # 하이라이트 종료 콜백이 전리품을 이어받는다
    return _try_start_victory_loot_phase(registry, owner, reset_game_callback)
```

**하이라이트 종료 콜백은 전리품과 동일한 폴백 사다리를 그대로 가져야 한다.**
`_finish_victory_loot_phase`가 `show_stage_clear_result` → `reset_game` 순으로
떨어지는 것과 같이, 하이라이트 종료도 `_try_start_victory_loot_phase` 실패 시
`_show_stage_clear_result` → `reset_game`으로 이어져야 한다. 이걸 빠뜨리면
전리품 시작 실패 시 결과화면에 영영 못 간다(소프트락).

시작 실패(클립 0개, 모듈 부재)는 `false` 반환 → 기존 래더가 그대로 진행.

## 3. 정규화 경계 (핵심 계약)

```
stage별 actor_context
        ↓ 실제 build/merge  ← BattleDrawActorContext.build() 최종 반환값
정규화된 ReplayActorSnapshot
(texture / src_rect / dest_rect / flip / tint)
        ↓
전용 하이라이트 렌더러
```

### 3.1 왜 이 경계인가

기록기가 스테이지별 원시 포즈 키를 직접 알면 스테이지가 늘 때마다 기록기가 깨진다.
그리고 [battle_draw_actor_context.gd](../godot/scripts/core/battle_draw_actor_context.gd)에는
같은 이름의 dict가 **두 개** 존재한다 —
[:109](../godot/scripts/core/battle_draw_actor_context.gd#L109) `combined_result_context`
(텍스처 sync용)와 [:818](../godot/scripts/core/battle_draw_actor_context.gd#L818)에서
반환되는 렌더러 대면 `actor_context`. 전리품 페이즈가 앞쪽에만 merge해서 보스가
일반 포즈로 남은 회귀(91bff66ab)가 바로 이 혼동이었다.

**기록기는 `build()`의 최종 반환값만 입력으로 받는다.** 중간 dict 접근 금지.

### 3.2 리졸버 계약

```gdscript
# victory_highlight_actor_resolver.gd
# ⚠️ 반환형 금지 — 매 프레임 중첩 Dictionary를 새로 만들면 "녹화 중 무할당"과
#    정면 충돌한다. 사전 할당된 슬롯에 in-place로 채운다.
static func resolve_into(actor_context: Dictionary, slot: Dictionary) -> bool
# slot 은 링버퍼가 소유한 고정 슬롯. 채우는 필드:
#   slot["player_texture"] : Texture2D   slot["player_src"]  : Rect2
#   slot["player_dest"]    : Rect2       slot["player_flip"] : bool
#   slot["player_modulate"]: Color
#   slot["boss_*"]         : 동일 5필드
# 반환 false = 텍스처 해석 실패 → 그 샘플은 실루엣 폴백으로 표시(슬롯은 재사용).
```

슬롯은 **평면 키**로 잡는다(중첩 dict 금지 — 중첩은 슬롯 재사용 시 내부 dict를
또 만들게 된다).

`actor_context`는 시트 후보를 **여러 키로 동시에** 싣고(`boss_walk_left_sheet`,
`boss_idle_sheet`, `boss_attack_sheet`, `boss_hit_sprite_sheet`, …), 최종 선택은
스테이지 액터 렌더러 안에서 일어난다. 리졸버는 그 선택 로직의 **공용 1벌**이며,
상태 플래그(`boss_is_walking` / `boss_hit_active` / `boss_facing` /
`boss_idle_frame` / `boss_sprite_frame`)와 셀 그리드 상수
(`boss_walk_frame_count` / `boss_walk_grid_cols`)를 읽어 `src_rect`를 만든다.

위치·크기는 이미 최종값이 실려 있다 — `boss_pos`(= `boss_draw_pos`, 파워로스
진동 오프셋 가산 후), `boss_sprite_draw_size`, `boss_visual_center_y_offset`,
`player_pos`, `player_paddle_size`.

**스테이지 탈출구**: 스테이지 렌더러가
`resolve_replay_actor_snapshot(actor_context) -> Dictionary`를 제공하면 그쪽을
우선한다(`has_method` 게이트). 1차 슬라이스는 공용 리졸버만 구현하고 훅은
미구현 — 필요해지는 스테이지가 나오면 2차에서 추가.

⚠️ **커버리지는 검증 대상이다.** 공용 리졸버가 S1~S8 각 보스에서 올바른 시트를
고르는지 Codex가 스테이지별로 확인하고, 실패하는 스테이지는 문서에 기록한 뒤
실루엣 폴백으로 처리한다. "전 스테이지 동작"을 미검증 상태로 주장하지 말 것.

### 3.3 샘플 스키마

⚠️ **스트림이 둘이다.** 드로우 경로 샘플만으로는 물리 이벤트를 정확히 기록할 수
없다 — 한 렌더 프레임 사이에 물리틱이 여러 번 돌면 타격·벽·골이 통째로 누락된다
(렌더 48 / 물리 72 조합에서 실제로 발생).

```
[시각 스트림]  드로우 경로 (build() 반환값 → resolve_into)
  capture_time_sec : float     # ⚠️ 절대 시각. 클립 시작 기준 정규화는 승격 시점에.
  ball_pos         : Vector2
  ball_radius      : float
  player_texture / player_src / player_dest / player_flip / player_modulate
  boss_texture   / boss_src   / boss_dest   / boss_flip   / boss_modulate

[이벤트 스트림]  물리·득점 경로
  capture_time_sec : float     # 같은 시간축
  kind             : int       # player_hit / boss_hit / wall / goal
  pos              : Vector2
```

승격 시 두 스트림을 **같은 시간축으로 결합**하고, 그때 비로소 클립 시작 기준
`t_sec`으로 정규화한다. 링버퍼 안에서는 절대 시각을 유지할 것 — 상대 시각으로
저장하면 evict마다 전 샘플을 다시 써야 한다.

텍스처는 **참조만** 보관한다(복사 없음). 참조 보유는 재생 시점까지 시트가 살아
있음을 보장하는 부수 효과가 있어 바람직하다. 클립은 매치 리셋에서 전량 해제한다.

## 4. 기록기

### 4.1 샘플레이트 — 물리틱이 아니라 렌더 프레임

`build()`는 [battle_draw_context.gd:36](../godot/scripts/core/battle_draw_context.gd#L36)
`build_actor_context`를 통해 **드로우 경로**에서 호출된다. 따라서 샘플은 렌더
프레임 레이트로 들어온다(`Engine.physics_ticks_per_second` 아님).

그리고 렌더 캡은 고정이 아니다 — Stable Monitor는 모니터에 따라 60/72/90 등으로
갈리고 사용자가 설정을 바꿀 수도 있다.

⚠️ 그렇다고 "최악값 240Hz"로 잡을 수도 없다. 디스플레이 설정에 Monitor /
Unlimited가 있어 360Hz 이상도 가능하다 — 상한을 하드웨어에 맡기면 안 된다.

**해법: 기록 상한을 두고 시간 게이트로 샘플링한다.**

```
MAX_CAPTURE_HZ  := 120          # 이보다 자주 들어오는 프레임은 건너뛴다
MAX_RECORD_SEC  := 2.0
CAPACITY        := MAX_CAPTURE_HZ * MAX_RECORD_SEC + margin   # 고정, 1회 사전 할당

- 드로우 프레임마다: now - last_capture < 1/MAX_CAPTURE_HZ 면 return (샘플 스킵)
- 링버퍼는 append / pop_front 를 쓰지 않는다 —
  고정 배열 + head / write_index / count 를 이동시키는 순수 인덱스 연산
- evict = head 전진뿐(원소 삭제 없음). 슬롯은 재사용된다.
```

재생 길이는 여전히 타임스탬프 보간이라 캡처 레이트와 무관하게 일정하다.
120Hz 상한은 1.1초 클립에서 132샘플 — 시각적으로 충분하다.

`MAX_RECORD_SEC := 2.0`. 클립 본편은 1.1초 이하지만, "마지막 플레이어 타격"이
그보다 앞설 수 있으므로 여유를 둔다.

**녹화 중 할당 0**이 계약이다. `resolve_into`(§3.2)로 슬롯을 in-place 갱신하고,
승격 시점에만 구간을 복사한다. 이벤트 스트림도 같은 방식의 고정 링이다.

### 4.2 클립 승격

훅 = [match_score_event_controller.gd:11](../godot/scripts/core/match_score_event_controller.gd#L11)
`handle_score_event`의 `scoring_side == "player"` 분기. 득점 판정 자체는
[match_score_state.gd:73](../godot/scripts/core/match_score_state.gd#L73) `score_for`
단일 지점이다.

클립 구간 = **마지막 플레이어 타격 −0.2초 ~ 골 통과 +0.25초(짧은 정지)**.
그 시작점이 버퍼 밖이면 버퍼 선두부터.

⚠️ **골 +0.25초 프레임은 승격 시점에 아직 존재하지 않는다.** 득점 훅은 골이 난
그 프레임에 돌기 때문이다. 미래 샘플을 기다리지 말고 **마지막 샘플을 0.25초 유지하는
합성 홀드**로 정의한다(정지 프레임 + 표식 표시 구간으로도 그 편이 낫다).
"뒤 0.25초를 더 녹화한다"는 설계는 채택하지 않는다 — 득점 직후 프레임은 이미
스코어보드 상태로 넘어가 시각적으로 다른 화면이다.

### 4.3 극적도 지표

일부는 기존 런타임에 있고, 일부는 **기록기가 직접 계산해야 한다**.

| 지표 | 출처 |
|---|---|
| 랠리 길이 | [ball_intensity.gd:124](../godot/scripts/ball/ball_intensity.gd#L124) `get_rally_count()` — 기존 |
| 매치포인트 / 듀스 | `match_score_state.would_score_finish` / `deuce_mode` — 기존 |
| 마지막 타격 주체·기술 태그 | 볼 업데이트 컨텍스트 — 기존 |
| 골 시점 공 속도 | **기록기가 샘플에서 산출**(득점 컨트롤러로 전달되지 않음) |
| 보스 패들 근접 통과 거리 | **기록기가 샘플에서 산출**(어디에도 기록되지 않음) |

공속 단위는 px/frame이다(base 7.65 / 캡 26) — 초당 값으로 오해하지 말 것.

### 4.4 선별 — 종류 분리 (가중치 상위 3개 아님)

1. **최종 결정타** — 매치를 끝낸 골. 무조건 포함(보장 1개).
2. **가장 긴 랠리** — `rally_count` 최대. 임계 미달이면 채택 안 함.
3. **한 자리 경합** — 기술 결정타 / 근접 통과 / 역전 동점골 중 최고 1개.

최종 1~3개 가변. 2·3번은 각자 임계를 넘겨야 채택되므로 평범한 승리에서는 1개만
나온다. 재생 순서는 시간순.

## 5. 재생

### 5.1 타임라인

- 클립당 **0.75~1.1초**, 전체 **2.8~3.2초** 상한(전환 포함).
- 클립 사이 짧은 전환(교차 페이드 또는 먹선 와이프) 0.12초.
- 골 통과 후 짧은 정지 후 다음 클립.

### 5.2 프레임 게이트

[battle_frame_flow_controller.gd:31](../godot/scripts/core/battle_frame_flow_controller.gd#L31)의
전리품 분기 **위**에 하이라이트 분기를 추가한다. 전리품보다 더 강하게 동결한다.

```gdscript
# 재생 중: 재생 상태 갱신 + redraw 만.
# update_player_control / update_active_items / update_ball / update_boss_ai /
# update_lingpet / update_effects 전부 호출하지 않는다.
```

전리품과 달리 플레이어 조작도 막는다(스펙: 플레이어·공·보스 AI·액티브 아이템 정지).

deps 등재 필수 — [battle_frame_flow_deps_builder.gd:40](../godot/scripts/core/battle_frame_flow_deps_builder.gd#L40)에
전리품이 등재된 것과 같은 자리. ⚠️ 빠지면 게이트가 **항상 false인 공허**가 된다
(퍽 모달이 정확히 이 함정을 밟은 적 있음 — 스모크는 키를 직접 주입해 GREEN).

### 5.3 그리기

#### 클리핑 — 전용 fx 호스트 필수 (배틀 캔버스 직접 draw 금지)

⛔ **immediate `_draw`는 자동 클리핑되지 않는다.** 게임 좌표계에서
`(game_offset, render_scale)` 캔버스 transform을 쓰는 오버레이는 **반드시**
`clip_contents = true`인 Godot Control 안에서 그려야 한다. 호출 체인 어디서든
`draw_set_transform(IDENTITY)` 리셋이 한 번만 일어나면 이후 draw가 화면 절대
좌표로 떨어져 레터박스 필러로 샌다. 정본은
[Host Coordinate Reality](skill_vfx_workflow.md#host-coordinate-reality)와
[GRT-045](godot_runtime_traps.md#grt-045)다.

레퍼런스 구현을 그대로 따를 것 — `stage_ball_spawn_intro_fx_host.gd`가
`_playfield_clip` Control + 드로우 브리지를 소유하고, 대응하는 lifecycle 모듈은
배틀 씬 캔버스에 `_draw_*(canvas)`를 **의도적으로 호출하지 않는다**.

- 클립 Control: position `Vector2.ZERO`, size = GAME_SIZE(760x750),
  `clip_contents = true` (fx-host-local 공간 기준).
- ⚠️ 레거시 80px 필러 인셋(x=80..680)으로 좁히지 말 것 — 실제 플레이 픽셀이
  잘리고 누수도 안 막힌다. 클립은 **풀 게임 캔버스**와 일치해야 한다.
- 호스트는 자체 `_process()`를 두지 않는다. 재생 상태가 갱신을 주도하고,
  **종료 · F9 직행 · 매치 리셋 각각에서 호스트를 명시적으로 숨기고 해제**한다.
  (자체 process를 두면 프레임 게이트 밖에서 계속 돌아 동결 계약이 깨진다.)

#### 레이어 순서

1. **불투명 먹색 재생판** `Rect2(0, 0, 760, 750)`.
2. 궤적 — 적금색, 꼬리로 갈수록 페이드.
3. 액터 스냅샷 2개(`draw_texture_rect_region`).
4. 표식 — 짧은 라벨 + 클립 인덱스 점.

⚠️ **반투명 스크림 + 라이브 액터 존치는 1차에서 채택하지 않는다.** 라이브 액터는
동결된 **현재** 위치에 있고 리플레이 액터는 **과거** 위치에 있어, 반투명이면 둘이
겹쳐 보인다(보스가 둘로 읽힘). 1차는 완전 불투명 재생판으로 라이브 씬을 덮는다.
반투명으로 가려면 **라이브 액터 드로우 억제 계약**을 별도로 추가하고 픽셀 QA를
통과해야 한다 — 시각 검증 전에 "억제 불필요"를 확정하지 말 것.

## 7. 이 레포 기왕 함정 (전리품 페이즈가 실제로 밟은 것)

1. **렌더러 대면 dict 누락** — §3.1. 씰은 소스 문자열이 아니라 실제 `build()`
   반환값을 관통해야 한다.
2. **deps 빌더 미등재로 게이트가 항상 false** — §5.2. 스모크가 키를 직접 주입하면
   공허 GREEN.
3. **owner 스키마 미선언 `set()` no-op** — §6 #2.
4. **match_reset 미등재** — 활성 하이라이트가 다음 매치 프레임플로우를 하이재킹.
5. **모달 중첩** — 재생 중 신화 시네마틱 / 퍽 선택이 열릴 일은 없어야 하지만
   (하이라이트가 보상보다 앞), 전리품처럼 방어 분기를 넣을지 확인.
6. **스모크 공허 GREEN** — typed 객체에 미선언 프로퍼티 대입은 그 레그 함수만
   중단시키고 러너는 `ok`를 찍는다. 표준 러너 `run_smoke_tests.ps1` 관통 필수.

## 8. 씰 (스모크)

**씰은 2벌로 나눈다.** 한 파일에 섞으면 헤드리스 배치가 픽셀 레그 때문에 통째로
불안정해지고, 반대로 픽셀 레그가 구조 레그에 묻혀 SKIP이 PASS로 읽힌다.

| 파일 | 실행 환경 | 범위 |
|---|---|---|
| `tests/victory_highlight_replay_smoke.gd` | 헤드리스(표준 러너 락스텝) | 구조·계약·게이트 (§8.1) |
| `tests/victory_highlight_replay_clip_pixel_qa.gd` | **비헤드리스 전용 래퍼** | 실제 렌더 클립 픽셀 (§8.2) |

⛔ **픽셀 파일 이름은 `*_smoke.gd`가 아니어야 한다.**
[run_smoke_tests.ps1:24](../godot/tools/run_smoke_tests.ps1#L24)는 `-Tests` 인자가
없으면 `tests/*_smoke.gd`를 **글롭으로 전량 자동 수집**하고,
[:44](../godot/tools/run_smoke_tests.ps1#L44)에서 **항상 `--headless`**로 돌린다.
`run_pre_push_checks.ps1` 전체 실행도 같은 글롭을 탄다. 즉 목록 등재 여부와 무관하게
파일명만으로 끌려 들어가므로, `*_smoke.gd` 이름으로 헤드리스 비-0 종료를 하면
**전체 스모크 배치가 항상 RED**가 된다. `_qa.gd` 접미사로 글롭 밖에 둘 것.

전체 라이브 QA(액터 포즈·표식 텍스트·속도·미감)는 씰이 아니라 별도 항목으로 유지.

### 8.1 헤드리스 구조 씰 — 최소 레그

1. **정규화 관통** — 실제 `BattleDrawActorContext.build()` 반환 dict → 리졸버 →
   렌더러 입력까지. 픽스처는 스테이지 픽스처를 실제로 태울 것(소스 단언 금지).
2. **레이트 불변** — 60Hz / 72Hz / 90Hz 샘플 시퀀스를 넣어 재생 길이가 동일함.
3. **링버퍼 시간 evict** — `MAX_RECORD_SEC` 초과분이 빠지고 할당이 늘지 않음.
4. **선별 종류 분리** — 평범한 승리 = 1개(결정타만), 장기랠리+역전 있는 승리 = 3개.
5. **래더 인터셉트 — 두 경로 각각** ⚠️ 정규(직접 호출)와 폴백(콜백 바인딩)을
   **별개 레그로** 태울 것. 한 경로만 통과해도 GREEN이 되면 §1의 결함을 못 잡는다.
   종료 후 전리품 → 전리품 실패 시 결과화면까지 이어지는 폴백 사다리 레그 포함.
6. **2스트림 결합** — 렌더 프레임 사이에 물리 이벤트가 2회 이상 들어간 픽스처에서
   타격/골이 누락되지 않음. ⚠️ 렌더=물리 1:1 픽스처는 이 결함을 못 잡는다.
7. **합성 홀드** — 득점 훅 시점에 미래 샘플이 없어도 골 뒤 0.25초 정지가 생성됨.
8. **무할당** — 랠리 N초 녹화 전후로 링버퍼 배열 크기가 불변이고 슬롯이 재사용됨.
   `MAX_CAPTURE_HZ` 초과 프레임이 스킵되는 것도 함께 단언.
9. **클립 호스트 구조** — 호스트 부모 관계, `clip_contents = true`, rect가 풀 게임
   캔버스(760x750)와 일치, lifecycle(종료·F9·매치리셋에서 숨김/해제).
   ⚠️ 이 레그는 **실제 클립을 증명하지 못한다** — §8.2가 본체다.
10. **F9 통과** — 재생 중 F9가 하이라이트에 소비되지 않고 결과화면 직행에 도달.
11. **프레임 게이트** — 재생 중 `update_ball` / `update_boss_ai` /
    `update_player_control`이 호출되지 않음(콜백 카운트 단언).
12. **스킵** — 1회 입력이 전체를 종료. 진입 직후 0.15초 무시창.
13. **리셋** — 매치 리셋 · 종료 · F9 각각에서 클립·텍스처 참조 전량 해제,
    **fx 호스트 숨김/해제**, `owner` 플래그 false.

### 8.2 비헤드리스 클립 픽셀 씰 — **1차 완료 조건 (필수)**

구조 씰만으로 1차를 넘기지 말 것. 이건 미관 검사가 아니라 이 레포에서 **이미
회귀가 발생한 좌표·클리핑 계약**이다. 선례
[smasher_plasma_clip_letterbox_pixel_smoke.gd:3](../godot/tests/smasher_plasma_clip_letterbox_pixel_smoke.gd#L3)이
"구조 GREEN인데 픽셀 클립은 실패"(`CLIP_CHILDREN` 마스크 사례)를 명시하고 있다.

범위는 **격리 호스트 10여 프레임 렌더**면 충분하다 — 풀매치 캡처 불필요.

**최소 합격 조건**

| # | 조건 |
|---|---|
| 1 | `game_offset != Vector2.ZERO` (0이 아닌 오프셋) |
| 2 | `render_scale != 1.0` (1.0이 아닌 배율) |
| 3 | clip **OFF** 대조군에서 좌·우 레터박스 누출 픽셀 **> 0** (누출 감지 능력 증명) |
| 4 | clip **ON**에서 좌·우 레터박스 누출 픽셀 **== 0** |
| 5 | 플레이필드 **내부**에 실제 하이라이트 픽셀 **> 0** (빈 화면 통과 방지) |
| 6 | 게임 x=0~80 / x=680~760 **내부** 표본도 lit — 레거시 80px 인셋 오적용 반증 |
| 7 | 비헤드리스인데 뷰포트 이미지를 못 얻으면 **fail-closed**(성공 종료 금지) |

조건 3은 대조군이다 — 이게 없으면 "아무것도 안 그려서 0"이 통과한다.
조건 6은 §5.3의 "80px 인셋으로 좁히지 말 것"을 실측으로 봉인한다.

**실행 계약 (러너 글롭과 공존)**

- 파일명 `victory_highlight_replay_clip_pixel_qa.gd` — `*_smoke.gd` 글롭 밖.
- **구조 씰만** 표준 헤드리스 러너와 CI 락스텝에 등재한다.
- 픽셀 QA는 **전용 비헤드리스 실행 래퍼**에서만 돌린다(`--headless` 금지).
- 래퍼의 판정 규약:
  - 명시적 `victory_highlight_replay_clip_pixel_qa: ok` 마커를 **요구**한다.
    마커가 없으면 실패.
  - 캡처 실패(뷰포트 이미지 없음) → **비-0**.
  - 헤드리스 오실행 감지 → **비-0**(마커 출력 금지).
  - **미실행 · 디스플레이 부재를 PASS로 보고하지 않는다.**

⚠️ 선례 파일
[smasher_plasma_clip_letterbox_pixel_smoke.gd:31](../godot/tests/smasher_plasma_clip_letterbox_pixel_smoke.gd#L31)은
헤드리스에서 `skipped` 뒤 `ok`+`quit(0)`을 찍는데, 이는 **자동 글롭과 공존하려는

## 12. 프로브 2 — HUD 포함 블릿 캡처 (2026-08-09 사용자 승인)

### 12.0 경위 — 프로브 1 판정 기록과 재분석

프로브 1(컴퓨트 크롭·다운샘플 아키텍처)은 **core GREEN / promotion RED**로
종결됐다. RED 2건:

| # | 실측 | 재분석 |
|---|---|---|
| HUD 혼입 3,360px | 현 배틀 렌더러에 pre-HUD 뷰포트 없음 | **정책이었다.** 원본 리플레이는 HUD 합성 프레임을 그대로 녹화했다(`replay_system.py` 주석: *"1300x846 HUD 합성 프레임을 60fps 원본으로 저장하면…"*). 캡처 프레임에 찍힌 HUD는 그 순간의 것이라 자기일관 — "라이브 HUD vs 과거 장면" 불일치 우려와 다른 문제다 |
| GPU worst 16.0~20.2ms · **min 4.35~5.12ms** (3회 실행 일관) | 1.0ms 게이트 20배 초과 | **그 아키텍처의 스케줄링 비용이다.** 380×375 텍스처 샘플+쓰기는 RTX 5070에서 μs 단위 — 측정된 5ms 바닥은 물리 비용의 ~1000배로, 렌더 스레드 밖 컴퓨트 디스패치+동기화에 귀속된다 |

**정책 개정(사용자 승인)**: HUD **포함** 캡처. 레터박스 필러는 크롭으로 계속
배제. 이는 실패한 프로브의 게이트를 몰래 완화하는 것이 아니라, 원본 선례에
근거한 **명시적 설계 결정 변경 + 다른 아키텍처를 같은 잣대로 재는 것**이다.

### 12.1 아키텍처 — 블릿 경로 (컴퓨트 셰이더 금지)

```
루트 뷰포트 (HUD 합성 완료, game_offset/game_size에 게임 영역)
  → 380×375 블릿 SubViewport
     (TextureRect가 루트 텍스처의 game rect 영역만 표시, linear 필터가 다운샘플)
  → 같은 크기 texture_copy 570KB → 링 슬롯
```

- 다운샘플 = 래스터 linear 필터. 컴퓨트 디스패치·uniform set·배리어 없음.
- 30Hz 게이트 = 캡처 틱마다 `UPDATE_ONCE` 재무장. `UPDATE_ALWAYS` 금지
  (72Hz 렌더에서 낭비).
- 캡처 카피는 `frame_post_draw`에서 **불변 요청 구조체**
  (frame_serial · capture_epoch · logical_time_sec · source/target) 소비 —
  §확정된 렌더 스레드 값-전달 계약 유지. 기록기 필드 재조회 금지.

  대응). 하드코딩 금지.

### 12.3 프로브 2 신규 검증 항목

1. **블릿 합법성** — SubViewport가 루트 뷰포트 텍스처를 샘플할 때 피드백 루프

   **한 프레임 늦은 내용**이 기대값이다 — 이것이 안정적으로 성립하는지가 이
   프로브의 1차 존재 이유다.
2. **신선도 실측** — 프레임 시리얼 스와치(프로브 1 방식 재사용)로 캡처 프레임의
   실제 지연을 측정해 기록한다. 골 정렬 허용 오차 = 캡처 간격 33ms + 1프레임
   지연(72Hz 기준 ~14ms) ≈ **최대 ~47ms 스테일**. 실측치가 이 안이면 통과,
   초과하면 원인 규명 전 승격 불가.
3. **크롭 정확성** — 게임 영역 네 코너 마커가 380×375의 대응 위치에 정확히
   오고, 필러 영역 픽셀이 캡처에 0인가.
4. **구현** — 기존 `victory_highlight_gpu_capture_probe_qa.gd` + 래퍼를 개조한다
   (VRAM 추적·폴백 주입·verdict 출력 인프라 재사용, 캡처 경로만 교체).
   `_qa.gd` 접미사 유지(스모크 글롭 밖).

## 13. 스틸 3컷 프로브 — `texture_get_data_async` (2026-08-12 사용자 확정)

### 13.0 결정

화면 녹화(연속 캡처)는 §12.4로 종결. 다음 후보 = **결정타 스틸 3컷**.
B안 포즈 측정은 **폐기가 아니라 보류** — 스틸 판정 후 대체/보강 결정에 따라
운명이 갈린다. 스틸은 per-frame 캡처가 아니라 **득점 이벤트당 1회 비동기
리드백**이므로 §12의 1.0ms per-frame 게이트 자체가 적용되지 않는다.

### 13.1 아키텍처 — §12 GREEN 자산 재사용

§12에서 픽셀 검증을 통과한 **HUD 블릿 뷰포트를 그대로 재사용**한다
(380×375 · HUD 포함 · 동적 game rect 크롭 · 코너 마커 검증 완료).
루트 전체를 직접 읽는 방식은 쓰지 않는다.

```
평상시: 블릿 뷰포트 비활성 — 캡처 비용 0
플레이어 득점: UPDATE_ONCE 재무장 → 블릿 1프레임 →
  블릿 텍스처에 직접 texture_get_data_async()   (링 texture_copy 없음)
콜백(요청 시점 데이터 보장, 문서 계약):
  → 결정타 / 장기랠리 / 역전 후보 슬롯에 배치
  → 각 부문 최고 후보만 온라인 교체, 최대 3장 유지
실패 · epoch 변경 · 지원 불가 → 폐기 → 상태 리플레이 폴백
```

- ⚠️ **경기 종료 후 과거 화면은 재취득 불가**다. 최종 3장이 정해질 때까지
  기다리면 늦는다 — **매 플레이어 득점마다 요청하되 부문별 최고 3장만
  온라인 유지**가 유일한 전략이다. 무승부 연장이 길어져도 메모리는 고정된다.
- 블릿은 루트보다 먼저 렌더되어 **한 프레임 늦은 내용**이 기대값(§12.3 실측
  시리얼 지연 1프레임). 득점 프레임 → UPDATE_ONCE → 다음 프레임 블릿 →
  async 요청의 체인이 실제로 골 화면을 담는지는 **프로브가 시리얼·점수로
  검증**한다(가정 금지).
- 메모리: 380×375×4 = 570KB/장 × 3장 ≈ **1.71MB CPU RAM** + in-flight 임시
  + 블릿 뷰포트 VRAM 0.57MB. 사실상 무시 가능하나 상한은 명시적으로 건다.

### 13.2 프로브 게이트 (사전 등록)

1. **평상시 캡처 비용 0** — 블릿 비활성 상태에서 프레임 비용 대조 실측
   (단언이 아니라 측정).
2. **득점 이벤트당 비동기 요청 정확히 1회**.
3. **HUD 포함 · 필러 0 · 네 코너 마커 · 시리얼 · 골 점수 정렬** 확인.
4. **최대 보관 3장 + in-flight 요청 상한**(연속 득점 폭주 방지).
5. **epoch 검증** — 점수/매치 리셋·메뉴 전환 시 이전 epoch 콜백 폐기.
6. **요청 프레임과 이후 프레임들의 72Hz 마감 측정** — async 리드백의 실제
   지연 영향(콜백은 frame_queue_size 프레임 뒤 도착).
7. **실패·지원 불가 강제 주입 → 상태 리플레이 폴백** 실작동.
8. **실 Vulkan 캡처 스틸을 저장해 미감 확인 후에만 제품 연결**
   — 기술 GREEN ≠ 제품 연결. 미감 판정은 사용자 소유.

### 13.3 판정 분기 (사전 등록)

- **GREEN + 미감 승인** → 제품 연결 핸드오프 작성. 그 시점에
  **대체 vs 보강** 결정(대체=B안 자연 소멸 / 보강=B안 측정 재개).
- **RED** → B안 측정 재개(플래그 존치 중).

### 13.4 §12.5 계측 표현 교정 (기록)

copy 4.4ms+ vs frame GPU 0.08~0.11ms의 비정합에서 "4.4ms 전부가 동기화
대기"라고 단정하는 것은 과하다 — **전송·리소스 전이·제출 대기·타임스탬프
범위가 섞였다는 추론**으로 기록한다. 향후 풀매치 리플레이 저장(.rpl류)을
재검토한다면 맞는 계기는 **S3/S7 OFF/ON 페어 프레임 차분**이다.

### 13.5 정리 계약

- `.tmp/victory_highlight_probe2_parse` — 독립 재현 종료로 삭제.
- §12.5 실측 기록 — 프로브 코드와 분리해 **문서만 좁은 커밋**으로 보존.
- 기존 untracked 프로브·래퍼 — **스틸 프로브가 블릿/크롭 코드를 승계한 뒤**
  제거(그 전에는 유일한 검증된 블릿 구현이므로 보존).
- B안 측정 플래그 — 스틸 판정까지 유지, 측정 플레이는 보류.

## 14. 프로브 4 — 원본 직역: 30Hz async 리드백 → CPU 링 (2026-08-12 승인)

### 14.0 경위

- §13 스틸 프로브는 **기술 GREEN·미감 RED**로 종결 — 사용자 판정: *"원본
  핑파이터처럼 녹화된 화면이 재생되는 느낌이 전혀 아님"*. 요구의 본체는
  정지컷이 아니라 **모션**이다.
- 프로브 1·2의 ~4.4ms 바닥은 **VRAM 링 `texture_copy` 경로**에 귀속된
  계측이었다. 프로브 3이 `texture_get_data_async`의 **요청·콜백 프레임 전체
  비용 0.023ms**(마감 초과 0)를 실측하며 세 번째 아키텍처의 근거를 만들었다.
- **원본은 VRAM 링을 쓴 적이 없다** — `HighlightRecorder`는 `screen.copy()`를
  CPU deque에 쌓았다. 이 아키텍처가 그 직역이다.
- **원본 풀매치 리플레이 = 50% 스케일·30fps** — 380×375·30Hz는 원본의 실제
  파라미터·느낌 재현이다.

세 조각이 각각 이미 GREEN이다: 블릿·HUD·크롭·30Hz 슬롯(§12 프로브 2) ·
async 리드백 프레임 비용(§13 프로브 3) · 재생 계약(1차 상태 리플레이).
**조합의 지속 거동만 미측정**이며 그것이 이 프로브다.

### 14.1 아키텍처

```
블릿 뷰포트 380×375 (§12 GREEN 자산: HUD 포함 · 동적 game rect · 30Hz UPDATE_ONCE)
  → 캡처 틱마다 texture_get_data_async(블릿 RD 텍스처)
     ⛔ texture_copy / VRAM 링 금지 — 프로브 1·2가 닫은 경로
  → 콜백(요청 시점 데이터)이 PackedByteArray를 CPU RAM 링에 저장
       링   = 2.0s × 30Hz = 60슬롯 × 570,000B ≈ 34.2MB
       클립 = 최대 3 × 1.1s × 30f = 99프레임    ≈ 56.4MB
       합계 상한 ≈ 91MB CPU RAM   (원본 투기장 하이라이트는 ~1.6GB였다)
  → 승격 = 득점 시 링 구간 참조 복사 (CPU, 논리 시각·2스트림 결합은 기존 계약)
  → 재생 = ImageTexture 1개 update() 30fps (570KB×30/s ≈ 17MB/s, VRAM 0.57MB 고정)
```

- 논리 시각 · 시각/이벤트 2스트림 · epoch · 모달 캡처 중단 + 겹침 클립 폐기 ·
  상태 클립 대체 사다리 · 재생 중 재캡처 차단 — **기존 확정 계약 전부 승계**.
- 슬롯 저장은 콜백 배열 **참조 보관**(추가 복사 금지). 엔진이 콜백마다 배열을
  새로 만드는 것은 API 특성이라 "할당 0" 계약은 **우리 코드의 추가 할당 0 +
  10초 지속 시 메모리 증가 0**으로 재정의한다.
- 구현은 §13 스틸 프로브 파일·래퍼를 **개조·승계**한다(블릿·async·epoch·폴백
  인프라 재사용).

### 14.2 게이트 (동일 잣대 — 낮춰서 GREEN 금지)

- **380×375 · 30FPS 고정.**
- 10초 지속 창(300요청): due=produced · 드랍 0 · **요청·콜백 프레임 worst
  ≤ 1.0ms** · 72Hz 마감 초과 0.
- CPU RAM: 링+클립 논리 상한 91MB 일치 · 10초 지속 시 증가 0(참조 교체 확인) ·
  매치 리셋/전환/메뉴 복귀 시 전량 해제.
- VRAM: 블릿 + 재생 텍스처만(≈1.2MB) · 정리 후 복귀.
- 신선도 시리얼 스와치 · 골 정렬(§12.3 승계) · epoch stale 폐기 ·
  폴백 강제 주입 2종(미지원/런타임 실패 → 상태 리플레이).
- **재생 실측 필수**: 99프레임 클립을 30fps로 실재생하며 `update()` 비용과
  프레임 마감을 측정한다 — 캡처만 재고 재생을 가정하지 말 것.
- verdict 분리 출력(technical / aesthetic PENDING_USER_REVIEW).

### 14.3 프로브 4 고유 검증 항목

1. **30Hz 지속 async 큐 거동** — in-flight 고수위, 스테이징 버퍼 경고 유무,
   콜백 지연 분포(요청→도착 프레임 수).
2. **콜백 수신 CPU 비용** — 570KB 수신이 30Hz로 누적될 때의 프레임 영향.
3. **콜백 스레드 확인** — 어느 스레드로 도착하는지 실측하고 링 쓰기 스레드
   규약을 명시(가정 금지).
4. **재생 `update()` 30fps 비용** — 재생 프레임들의 마감 실측.
5. **미감 = 모션 판정** — 실재생을 사용자가 본다. 기술 GREEN ≠ 연결.

### 14.4 판정 분기 (사전 등록)

- **GREEN + 미감 승인** → 제품 배선 핸드오프. 화면 녹화가 양식화 재생판을
  **대체**한다. **B안 소멸.** 스틸 3컷 체인은 부산물로 존치(결과화면 정지컷 등
  재활용 후보).
- **RED** → **수단 소진 확정.** 상태 리플레이(+원하면 스틸)가 최종이며,
  이후 캡처 아키텍처 재도전은 없다.

### 14.5 첫 실측 기록 + 계측 개정 — 이중 창 (2026-08-12 승인)

**첫 실 Vulkan 실측(독립 실행 2회)**: 단일 게이트 RED, 나머지 전부 여유 GREEN.
- GREEN: due=produced=300·드랍 0 / 콜백 지연 **정확히 2프레임(min=avg=max)** /
  요청·콜백 프레임 GPU worst 0.227~0.256ms(게이트 1/4) / 마감 초과 0 /
  **콜백 스레드=main 실측**(541회 전부) / 재생 99f@30fps update worst 0.203ms·
  마감 0 / 논리 90,630,000B 정확 일치·정리 해제·owned 0 / VRAM 피크 +2.6MB 복귀.
- RED: **10초 지속 CPU +65,344~68,352B**(2회 5% 이내 = 결정적, ~220B/요청).
  프로브 지표 저장소는 창 전 사전 할당돼 있어(창 안=인덱스 쓰기) 프로브 탓이
  아니다 — 엔진/할당자 측(유력: async 다운로드 스테이징 버퍼·풀 성장).
  1회 창으로는 웜업 플래토 vs 선형 누수 구분 불가(선형이면 ~23MB/h).

**개정(사용자 승인)**: 지속 창을 **2회 연속** 돌리고, "증가 0" 게이트는
**창 2(웜업 후)**에 적용한다. 임계 자체는 불변 — 기존 계측 계약(프레임=워밍업
후 교차, VRAM=1초+ 대기 3회 연속)과 동일한 웜업 규율이며 게이트 완화가 아니다.
- 창 2가 0이면 → 플래토 확정, 이 게이트 GREEN.
- 창 2도 선형 성장이면 → **진짜 누수**. 승격 불가, 할당 추적으로 원인 규명
  전까지 RED 유지. 창 횟수를 늘려 통과시키는 것은 금지.
- 창 1·창 2 delta를 모두 출력해 판정 근거를 남긴다.

### 14.6 차분 실험 A/B/C — 성장 소유자 특정 (2026-08-13 승인)

§14.5 이중 창 재실측이 계약상 RED로 종결됐다(창1 `+65,344B` / 창2 `+46,912B`,
독립 재현 시 **바이트 동일** = 완전 결정적). 나머지 게이트는 전부 큰 여유로
GREEN이다. 3번째 창 추가·임계 완화는 하지 않았다.

**코드 감사(정적, 확정 아님)**: 우리 경로엔 무한 성장 구조가 없다 —
`_store_cpu_ring_reference`는 고정 60슬롯 참조 교체(랩어라운드), `_ring_metadata`도
60 바운드, 지속 창 지표는 사전 할당 배열의 인덱스 쓰기,
`_fill_ring_and_promote_clips()`는 **창 브래킷 이전**에 실행되어 창 안에서 클립이
자라지 않는다. 창당 570,000B×300=171MB 처닝 대비 46,912B는 0.027%다.
⚠️ 정적 분석으로 확정하지 말 것 — 아래 차분 실험이 판정한다.

이 실험은 **계측 의미와 무관하게 유효**하다(`OS.get_static_memory_usage()`가
라이브 바이트인지 누적 풀인지 미확인 — context7 키 만료). 같은 계기로 잰
A와 C의 차이는 계기가 무엇을 재든 성립한다.

#### 실행 규약 (전부 필수)

- **A/B/C는 각각 새 프로세스**로 실행한다. 한 프로세스에서 순차 실행 금지
  (할당자 상태가 변형 간에 오염된다).
- **각 변형도 10초 창을 2회** 돌리고, 비교값은 **창 2 delta만** 쓴다.
- **세 번째 웜업 창 금지.**
- 링·클립 준비까지의 **공통 전처리는 완전히 동일**하게 유지한다.
- **세 변형 모두 독립 2회 재현**한다.
- **임의 허용오차를 만들지 않는다.**
- 측정 창 안에서는 **무거운 dict 집계·출력 금지**. 특히 현행
  `_callback_source_thread_counts[thread_id] = ...get(...)+1`은 콜백마다 도는
  dict 연산이므로 **창 안에서는 평범한 int 카운터로 바꾸고**, thread-id 요약은
  창 밖에서 만든다(이 dict 연산 자체가 성장 기여자일 수 있다).

#### 변형 정의

| | 블릿 | async | 콜백 검증·main 전달 | 링 저장 |
|---|---|---|---|---|
| **A** | 비활성(`UPDATE_DISABLED`) | 0건 | — | — |
| **B** | C와 동일 | C와 동일 | C와 동일 | `_store_cpu_ring_reference()`만 생략 |
| **C** | 현행 | 현행 | 현행 | 현행 |

A는 30Hz due 틱만 진행한다.

#### 판정 (사전 고정 — 사후 해석 금지)

| 결과 | 판정 |
|---|---|
| A window2 **==** C window2 가 독립 2회 모두 재현 | **엔진 베이스라인.** 그때만 `C − A = 0` 차분 게이트 개정을 *검토* |
| A=0, B=C>0 | **async 기구 소유** |
| A=0, B=0, C>0 | **링 참조 교체 경로 소유** |
| 그 외 / 재현 불일치 | **소유자 미확정 — 기존 RED 유지** |

⛔ `==`는 문자 그대로다. 현재 바이트 단위 재현성이 확보돼 있으므로 **정확한
delta 재현을 요구**하며, 맞지 않으면 자동 해석하지 않는다. "≈"를 사후
허용오차로 바꾸는 것은 금지한다.

⚠️ 차분 게이트 개정은 **실험 결과가 위 첫 행을 만족한 뒤에만** 검토 대상이
된다. 미리 열어두면 그 자체가 완화 통로가 된다.

**해석 주의(B)**: B는 저장을 생략하므로 배열이 즉시 해제되어 C와 **수명 패턴이
다르다**(C=60슬롯 뒤 해제). B<C가 나와도 "저장 호출이 할당한다"와 "60슬롯 보유가
단편화를 바꾼다"를 구분하지 못한다 — 둘 다 우리 측이라 조치는 같지만, 원인
서술을 단정하지 말 것.

**조건부 후속(이 실험 범위 밖)**: 결과가 "async 기구 소유"로 나오면, async 특유
문제인지 단순 570KB 블록 처닝인지를 가르는 변형 D(async 없이 570KB
PackedByteArray를 300회 할당·해제)를 별도 승인 후 검토할 수 있다.

### 14.7 차분 실험 결과 (2026-08-13 실측) — 기계적 판정 `UNRESOLVED_RED`

6회(A1→B1→C1→A2→B2→C2, 각 별도 프로세스) 실행. **모든 변형이 독립 2회에서
바이트 단위 동일 재현**.

| 변형 | window1 delta | **window2 delta (게이트)** | 재현 |
|---|---|---|---|
| **A** (블릿 비활성·async 0·저장 0) | 65,152 | **46,720** | 2/2 바이트 동일 |
| **B** (블릿·async·검증·전달, 저장만 생략) | 635,376 | **46,912** | 2/2 바이트 동일 |
| **C** (현행 전체) | 65,344 | **46,912** | 2/2 바이트 동일 |

전 변형 `due=300 produced=300 dropped=0`, 콜백 지연 2프레임, 마감 초과 0,
콜백 300회 전부 main thread(mismatch 0).

#### 기계적 판정 (§14.6 표 그대로 적용)

`A(46,720) != C(46,912)` — `==`는 문자 그대로이므로 1행 불성립.
`A != 0`이므로 2·3행도 불성립. → **4행: 소유자 미확정, 기존 RED 유지.**
러너도 `diff_owner_verdict: UNRESOLVED_RED`를 출력했다. 이 판정은 그대로 기록된다.

#### 데이터가 실제로 보여주는 것 (해석 — 판정 변경 아님)

- **A는 우리 캡처 작업을 하나도 하지 않는데 46,720B 성장한다.** 이는 C 성장분
  46,912B의 **99.59%**다. 유휴 대조군이 성장의 거의 전부를 설명한다.
- **`C − A = 192B`**. 그 사이에 C가 추가로 수행한 연산은 블릿 300 + async 300 +
  콜백 300 + 저장 300 = **1,200회**. 192 ÷ 1,200 = **0.16B/연산** —
  할당 단위(통상 ≥16B)보다 작으므로 **요청당 할당이 아니라 상수 오프셋**이다.
- **`B == C` 바이트 동일(46,912)** → `_store_cpu_ring_reference` 경로의
  기여는 **정확히 0**이다.
- B의 window1만 635,376으로 10배 높다(즉시 해제 → 웜업 할당 패턴 상이). 그러나
  window2에서 C와 완전히 수렴한다.

#### 미해결 — 승인 대기 제안 (적용 금지, 승인 전)

현 게이트 "고정 창에서 delta == 0"은 **상수 오프셋과 누수를 구분하지 못한다**.
누수는 연산 수에 비례하고 상수는 그렇지 않다. 제안:

- **요청 수를 바꾼 두 창으로 비례성을 검정한다.** 예: 창2를 300요청과
  600요청으로 각각 재고, `C − A`가 **192로 일정하면 누수 없음(GREEN)**,
  **384로 배증하면 요청당 누수(RED)**.
- 이는 임계 완화가 아니라 **계약 의도(우리 코드가 사용량에 비례해 새는가)를
  실제로 재는 검정**으로의 재정식화다. 다만 §14.6 1행이 정확 일치로
  성립하지 않았으므로 **사용자 승인 없이는 적용하지 않는다.**
- 대안: 192B의 정체를 직접 특정(블릿만/async만 분리 변형). 상수임이 이미
  강하게 시사되므로 비용 대비 효용은 비례성 검정이 높다.

### 14.8 비례성 검정 — 요청수 300 vs 600 (2026-08-13 승인)

**§14.7 해석 정정**: "C−A=192B는 1,200연산당 0.16B이므로 상수 오프셋"은
**가설이며 확정이 아니다.** 할당자 풀은 연산별 비용이 선형으로 드러나지 않을 수
있다(블록 단위 성장·지연 반환·단편화). 상수인지 비례인지는 **이 절의 실측으로만**
확정한다.

착수 근거: A가 C 성장의 99.59%를 설명하고 `B==C`가 바이트 재현되어, 비례성
검정의 정보 가치가 충분하다.

#### 실행 규약 (전부 필수)

- 캡처율 **30Hz 고정**.
- **모든 실행의 window1은 300틱 워밍업으로 동일**하게 유지한다.
- **window2만** 300틱 또는 600틱으로 달라진다.
- **A와 C만 측정한다. B는 재측정하지 않는다.**
- `A300 → C300 → A600 → C600`을 **각각 새 프로세스**로 실행하고,
  **전체 시퀀스를 2회 반복**한다(총 8프로세스).
- 지표 배열은 **최대 600개로 창 이전에 사전 할당**한다.
- **측정 창 안에서는 인덱스 쓰기만 허용**한다(집계·출력·dict 연산 금지).
- 메모리 측정은 **동일한 정착 프레임 뒤**에 수행한다.
- **허용오차 금지. 세 번째 창 금지.**

#### 판정값

```
D300 = C300_window2 − A300_window2
D600 = C600_window2 − A600_window2
```

| 결과 | 판정 |
|---|---|
| 두 반복이 **바이트 단위로 재현**되고 `D600 == D300` | **요청수 비례 성장 없음.** 메모리 게이트를 `D600 − D300 == 0`으로 개정하고 **기술 GREEN** |
| `D300 > 0` 이고 `D600 == 2 × D300` | **요청당 선형 누수. RED** |
| `D300 == D600 == 0` | **GREEN** |
| 그 외 / 반복 불일치 | **UNRESOLVED_RED 유지** |

⛔ `==`는 문자 그대로다. 사후 허용오차를 만들지 않는다.

#### 구현 참고

- window2가 600틱이면 20초이므로, 8프로세스 총 실행 시간이 늘어난다
  (창만 합산 ≈ 200초 + 프로세스별 오버헤드). 러너 타임아웃을 넉넉히 잡을 것.
- 측정 창 이후 단계(재생·스틸 저장 등)는 delta에 영향을 주지 않으나, 변형 간
  동일하게 유지해 비교 조건을 일치시킨다.
- 이 검정은 §14.6과 마찬가지로 **계측 의미와 무관하게 유효**하다 — 같은 계기로
  잰 두 차분의 비교이기 때문이다.

### 14.9 비례성 검정 결과 (2026-08-14) — 기술 GREEN

8프로세스 실행, **독립 2회 반복이 raw·diff 모두 바이트 단위로 재현**.

| 변형 | window2=300틱 | window2=600틱 |

| **A** (유휴 대조군) | 46,720 | 129,664 |
| **C** (전체 캡처) | 46,912 | 129,856 |
| **C − A** | **192** | **192** |

```
exact_raw_reproduction: true
exact_diff_reproduction: true
verdict: NO_REQUEST_PROPORTIONAL_GROWTH_TECHNICAL_GREEN
```

전 실행 `due==produced`·드랍 0·콜백 지연 정확히 2프레임·콜백 전부 main thread
(mismatch 0)·마감 초과 0.

#### 판정 (§14.8 표 1행)

`D600 == D300`이고 두 반복이 바이트 재현되었다 → **요청수 비례 성장 없음.**
메모리 게이트를 **`D600 − D300 == 0`으로 개정**한다(192−192=0 충족).
**프로브 4 기술 게이트 전부 GREEN.**

§14.7의 "상수 오프셋" 가설이 실측으로 확정됐다. 보강 근거 둘:
- window1(300틱 고정)의 차분도 `65,484 − 65,292 = 192`로 동일하다.
- **엔진 베이스라인 A는 초선형**이다(300→600틱에서 46,720→129,664 = 2.78배).
  우리 경로가 요청당 샜다면 D가 함께 커졌어야 하나 **192에서 전혀 움직이지
  않았다.**

#### 남은 승격 게이트

**모션 미감 판정 하나뿐이다.** 실제 99프레임 재생을 사용자가 보고 "원본처럼
녹화된 화면이 재생되는 느낌인가"를 판정한다. **기술 GREEN이 미감 통과를
대신하지 않는다**(§13에서 스틸이 기술 GREEN·미감 RED로 종결된 선례).

#### 운영 주석

검증 중 C600 1회가 **인터랙티브 가드**로 차단됐다(병렬 트랙의 Godot 프로세스가
실행 도중 출현). 프로브 결함이 아니며, 프로세스가 빈 뒤 재실행하여 8/8 통과했다.
이 레포에서 다중 프로세스 실측을 돌릴 때는 **시작 전뿐 아니라 실행 중에도**
병렬 작업이 끼어들 수 있음을 전제할 것.

## 15. 프로브 5 — 실제 게임 화면 캡처 (시각 전용) (2026-08-14 승인)

### 15.0 경위 — 왜 필요한가

§14.9로 기술 게이트가 전부 GREEN이 됐으나, 사용자가 재생 창을 실제로 보고
남긴 판정은 **"화면 캡처가 아니라 프로토타입 도형만 보인다"**였다.

원인: 프로브 4는 격리 환경이라 실제 게임을 띄우지 않고 `CaptureFixture`
(색 사각형·원·코너 마커)를 그려서 캡처했다. **캡처 기구는 진짜인데 피사체가
가짜**였다. 따라서 사용자의 원 질문 — *"원본 핑파이터처럼 보이는가"* — 은
아직 아무도 확인하지 못했다.

⚠️ 문서에 "합성 픽스처"라고 적어둔 것만으로는 판정 불가라는 사실이 전달되지
않았다. **미감 판정을 요청할 때는 판정 가능한 피사체를 먼저 준비할 것.**

### 15.1 목적과 비목적

- **목적**: 실제 스테이지·캐릭터·보스·HUD가 렌더된 화면을 380×375·30Hz로
  캡처해 재생하고, 사용자가 **미감을 판정할 수 있게** 한다.
- **비목적**: 성능 게이트 재판정. §14.9에서 종결됐으며 이 프로브는 그것을
  다시 열지 않는다. 제품 배선도 아니다.

### 15.2 구조

- 합성 `CaptureFixture` 대신 **실제 배틀 씬(`res://scenes/main.tscn`)**을
  띄운다. 창 렌더(Vulkan), 헤드리스 금지.
- 스테이지는 파라미터(`-Stage`, 기본 1). 최소 **S1과 S5** 두 번 확인할 것
  (S5는 §11에서 보스 시트 해석이 문제됐던 스테이지다).
- 캡처 경로는 §14.1 그대로 재사용한다 — 블릿 뷰포트 → 30Hz
  `texture_get_data_async` → CPU 링. **`texture_copy`/VRAM 링 금지**(§12 종결).
- 실전투를 수 초간 진행시켜 링을 실제 플레이 프레임으로 채운다. 랠리가
  일어나면 충분하며, **실제 득점까지 강제할 필요는 없다** — 판정 대상은
  "실제 화면이 녹화·재생되는 모습"이다.
- 링에서 99프레임 클립을 승격해 **창에서 30fps로 재생**한다.
- 재생 프레임 3장을 스틸로 저장해 기록에 남긴다.

### 15.3 보고 항목 (게이트 아님 — 관측 보고)

성능 수치를 **정보로만** 출력한다. 합성 픽스처는 드로우가 사소했으나 실제
스테이지는 VFX·다중 액터로 훨씬 무겁다. 따라서:

- 캡처·재생 프레임 비용, 마감 초과, 드랍, 콜백 지연을 §14 형식 그대로 출력.
- **§14.9 수치를 크게 상회하면 자동 RED가 아니라 신규 발견으로 보고**하고
  사용자 판단을 받는다. 이 프로브가 성능 게이트를 새로 만들지 않는다.
- verdict는 `visual_probe_ok` / `aesthetic_verdict: PENDING_USER_REVIEW`로
  분리 출력한다.

### 15.4 판정 (사용자 소유)

- **미감 GREEN** → 제품 배선 핸드오프 작성. 화면 녹화가 양식화 재생판을
  **대체**하고 **B안 구현 계획 폐기**.
- **미감 RED** → 기술 경로는 문서·프로브로 보존하되 **제품 승격하지 않는다.**
  1차 상태 리플레이가 제품 기준선으로 남는다.

실제 스테이지 아트의 해상도·가독성 최종 확인은 어느 쪽이든 **제품 배선 후
별도 실플레이 QA**로 남는다(이 프로브는 그 앞단의 판정 재료다).

### 15.5 구현 참고

- 프로브 4 파일(`victory_highlight_still_capture_probe_qa.gd`)을 개조하거나
  별도 파일로 분리하되, **`_qa.gd` 접미사를 유지**해 스모크 글롭 밖에 둔다.
- 실행 중 병렬 Godot 프로세스가 인터랙티브 가드를 트립시킬 수 있다(§14.9
  운영 주석). 시작 전·실행 중 모두 경합을 전제할 것.
- ⚠️ **standalone 프로브의 구 메모리 게이트 잔존**(프로브 4
  `:1086-1093`, `_diff_variant.is_empty()`일 때 `window2_delta != 0` → fail)이
  아직 정리되지 않았다. §14.9가 게이트를 `D600−D300==0`으로 개정했고 이는
  단독 프로세스가 구조적으로 평가할 수 없다. 단독 실행이 오독을 낳지 않도록
  **메모리 항목을 판정에서 제외하고 정보 출력 + "§14.9에 따라 차분 러너에서만
  판정" 표기**로 정리한다(임의 임계 신설 금지 — 완화가 아니라 평가 불가
  항목을 평가하는 척하지 않는 것).

## 16. 제품 배선 — 실 승리 흐름에 프레임 녹화·재생 연결 (2026-08-14 승인)

### 16.0 경위

§15로 실게임 화면 캡처가 S1·S5에서 확인됐다. 그러나 사용자가 인게임에서
스테이지 클리어 후 확인했을 때 **기존 상태 리플레이와 차이가 없었다** —
당연하다. 프로브는 제품에 연결된 적이 없다(프로브 2파일 untracked,
`godot/scripts/`에서 캡처 코드 참조 **0건** 실측 확인).

⚠️ **미감 판정의 올바른 맥락은 프로브 창이 아니라 인게임 승리 흐름이다.**
격리 프로브는 "기구가 작동한다"만 보여줄 뿐 최종 사용 맥락을 보여주지 못한다.
따라서 배선 후 인게임 판정으로 간다.

### 16.1 범위

- **범위**: 실 승리 흐름에 프레임 녹화·재생을 연결하고, 캡처 실패 시 기존
  상태 리플레이로 폴백.
- **비범위**: 성능 게이트 재판정(§14.9 종결) · 캡처 아키텍처 변경(§14.1 확정) ·
  해상도 변경(380×375 유지, 변경은 별건).

### 16.2 아키텍처 — 이중 레인

```
[프레임 레인] 신규
  블릿 뷰포트(380×375·HUD 포함·동적 game rect 크롭)
    → 30Hz texture_get_data_async → CPU 링 60슬롯 × 570,000B = 34.2MB
    → 플레이어 득점 시 프레임 클립 승격(최대 3 × 99프레임 ≈ 56.4MB)
    → 재생 = ImageTexture 1개 update() 30fps

[상태 레인] 기존 — 그림자로 계속 유지
  현행 스냅샷 기록·승격을 그대로 둔다. 모든 골을 계속 승격한다.
```

⛔ `texture_copy` / VRAM 링 금지(§12 종결). 현행 제품 기록기에는 프레임 레인이
**없다**(실측 0건) — 프로브에서 이식한다.

**렌더러 선택**: `victory_highlight_playback_state.start(clips, ...)`가 소비하는
클립에 프레임이 실려 있으면 **프레임 렌더러**, 없으면 **기존 상태 렌더러**를
고른다. 선택 지점은 `:67`의 renderer 조회 한 곳으로 모은다(분기 복제 금지).

**폴백**: RD 미지원(OpenGL/헤드리스) · RD 생성 실패 · 매치 중 런타임 실패 ·
저VRAM → 프레임 레인 포기하고 **상태 클립으로 재생**한다. 상태 레인이 그림자로
계속 돌기 때문에 매치 중 실패에도 대체할 클립이 있다(§14 확정 사항).
둘 다 없으면 하이라이트를 생략하고 상자 드랍으로 직행한다.

### 16.3 그대로 승계 (재구현 금지)

클립 선별(결정타·장기랠리·역전) · 스킵 입력 + F9 통과 · 상자 드랍 순서 ·
모달 캡처 중단 + 겹침 클립 폐기 · epoch · 논리 시각 · 밴드 변환과
`clip_contents` 호스트 · 승리 래더 2곳 인터셉트 · 기존 씰 전량.

### 16.4 제품 고유 관심사 (프로브에 없던 것)

1. **상시 녹화**: 프로브는 10초 창이었으나 제품은 **모든 랠리 내내** 돈다.
   링이 60슬롯 바운드라 메모리는 유한하나, **실매치 길이에서 정상 상태 증가가
   없는지** 확인한다(§14.9 계약과 동일 성질).
2. **프리웜**: 블릿 뷰포트·RD 자원·`ImageTexture`를 **스테이지 진입 시** 생성한다.
   첫 득점에서 지연 생성하면 이 레포의 hot-path lazy-init 트랩(GRT-003)이다.
3. **해제**: 매치 리셋 · 스테이지 전환 · 메뉴 복귀에서 링·클립·RD 자원 전량 해제.
4. **전시 하드웨어**: 배선은 기본 ON으로 하되(그래야 인게임 판정이 가능),
   **전시 빌드 출하 기본값은 별도 결정**으로 남긴다. 폴백이 실기에서 밟히는지
   확인 전에는 부스에서 처음 밟게 하지 않는다.

### 16.5 씰

1. 플레이어 득점 시 **프레임 클립이 승격**된다.
2. **렌더러 선택**: 프레임 있는 클립 → 프레임 렌더러 / 없는 클립 → 상태 렌더러.
   두 경로 모두 실 `start()`를 관통할 것(정적 단언 금지).
3. **폴백 강제 주입 2종**(기동 실패·매치 중 실패) → 상태 클립으로 재생,
   소프트락 없음, **상자 드랍까지 진행**.
4. 프레임·상태 **양 레인 모두 없을 때** 하이라이트 생략 + 상자 직행.
5. 매치 리셋 · 스테이지 전환 · 메뉴 복귀에서 **전량 해제**(소유 RID 0).
6. **그림자 상태 레인이 프레임 레인 활성 중에도 모든 골을 계속 승격**한다.
7. 기존 밴드 클립 픽셀 씰이 프레임 재생에서도 유효(문구 대역 침범 0).

### 16.6 실플레이 QA (배선 후, 사용자 소유)

**인게임에서 실제로 스테이지를 클리어**해 하이라이트를 본다. 최소 S1·S5.
판정 = *"원본처럼 녹화된 화면이 재생되는 느낌인가."*

- **GREEN** → 승격. B안(포즈 계약 정본화) **폐기**. 스틸 3컷 체인은 부산물 존치.
- **RED** → 프레임 레인을 기본 OFF로 되돌리고 상태 리플레이가 기준선.
  기술 경로는 문서·코드로 보존.

⚠️ 미감이 "느낌은 맞는데 흐리다"면 그것은 RED가 아니라 **해상도 안건**이다
(380×375는 VRAM 링 시절 유산이고 현 경로는 여유가 크다). 별건으로 분리해
풀해상도 재프로브를 검토한다.

### 16.7 선행 조건 / 미결

- ⚠️ **모달 논리 시계(§14 배선분)는 여전히 게이트 미해제**:
  `runtime_perk_modal_time_shift.gd`가 **HEAD에 0건**(실측). 다만 현행 1차 상태
  리플레이도 같은 벽시계 성질을 이미 안고 출하돼 있으므로, §16은 이를
  **악화시키지 않는 선에서 진행**한다. **프레임 레인은 상태 레인과 반드시 같은
  시각 경로를 쓴다** — 그래야 그 모듈이 랜딩할 때 두 레인이 한 번에 고쳐진다.
  별도 시계 신설 금지.
- 프로브 파일 2개는 여전히 untracked이며, 배선이 캡처 코드를 승계한 뒤 정리한다.

### 16.8 인게임 QA 결함 — 크롭이 좌상단 확대 (2026-08-14, 수정 계약)

**증상(사용자 실플레이, 풀스크린 4K)**: 프레임 리플레이가 재생은 되지만 내용이
**화면 좌상단 확대**다 — 골드 카운터·좌측 필러 HUD·플레이필드 왼쪽 가장자리만
찍히고 전투 장면(패들·공)이 없다. 프레임 경로 자체(캡처→승격→재생→스킵→패널)는
전부 동작했다. **남은 결함은 크롭 하나다.**

**원인(코드 실측 — `victory_highlight_frame_capture_state.gd:383-392`)**:

```gdscript
_blit_atlas.region = _build_game_rect(_root_viewport.get_visible_rect().size)
```

`get_visible_rect().size`는 **캔버스 단위**이고 `AtlasTexture.region`은
**텍스처(프레임버퍼) 픽셀**이다. 프로젝트는 `stretch canvas_items + expand`라
풀스크린 4K(3840×2160)에서 캔버스는 ≈2215×1246 — 스트레치 배율 ≈1.73배가
누락되어 캔버스 rect(≈476,0,1263,1246)가 픽셀 rect로 오적용, **좌상단
1263×1246 픽셀만** 크롭된다 = 관측 증상과 정확히 일치.
**GRT-046(캔버스 단위 vs 프레임버퍼 픽셀) 트랩 재발.**

**왜 프로브·픽셀 QA가 못 잡았나**: §15 프로브와 §16 픽셀 QA는 **윈도우드
기본 크기**에서 돌아 스트레치 배율이 1.0 — 캔버스 == 프레임버퍼라 두 단위가
우연히 일치했다. §8.2 픽셀 씰이 요구했던 `render_scale != 1.0` 선행 조건이
프레임 픽셀 QA에 승계되지 않았다.

**수정 계약**:

1. 크롭 rect를 **프레임버퍼 픽셀로** 계산한다. 우선 검토 = 레이아웃 권위
   (`battle_view_layout`)의 game rect를 **캔버스→프레임버퍼 변환(스트레치
   배율)** 해서 쓰는 것(자체 공식 재유도 = 공식 이중화). 최소 수정으로
   `_build_game_rect`에 루트 **텍스처 크기**(= 창 픽셀)를 넣는 것도 수학적으로
   동치이나(min-공식은 스트레치와 합성 시 불변), 동치 근거를 주석으로 남길 것.
2. **창 크기·전체화면 전환 시 재동기화**가 실제로 걸리는지 확인.
3. **씰 보강(필수)**: 프레임 픽셀 QA에 **스트레치 배율 ≠ 1.0** 조건을 추가
   (창 픽셀 ≠ 캔버스 크기인 창에서 실행). 반증 = 구 코드(캔버스 단위)가 그
   조건에서 RED임을 확인. 배율 1.0에서만 도는 픽셀 QA는 이 결함 클래스를
   구조적으로 놓친다.
4. 수정 후 **인게임 미감 판정 재시도**(S1·S5).

### 16.9 2차 인게임 QA 결함 — 범위 밖 샘플링 깨짐 (2026-08-14, 수정 계약)

**증상(사용자 실플레이, 4K 풀스크린, §16.8 수정 후)**: 리플레이 프레임의
**좌상단 ~57.7%(가로·세로 동일 비율)에만 정상 콘텐츠**(플레이필드 일부 + 우측
필러 HUD까지 포함, 세로로 압축됨), 나머지는 **세로 줄무늬 깨짐**(미초기화
텍스처 서명).

**기전 축소(코드 실측)**:
- 콜백 바이트 검증(`:314`)을 통과했다 → 깨짐은 리드백 크기 문제가 아니라
  **380×375 블릿 텍스처 안에 이미 들어 있다** = **블릿 렌더 시점에
  AtlasTexture가 소스 텍스처 범위 밖을 샘플링**했다.
- 57.7% = 4K에서 캔버스/프레임버퍼 비율(1246/2160). **region이 실제 샘플링
  텍스처보다 큰 크기 기준으로 계산**되어 정규화 시 u/v가 1.0을 넘은 서명이다
  (콘텐츠가 우측 필러까지 포함 + 세로 전체가 상단 57.7%로 압축 = u,v 초과 일치).
- §16.8은 `root_texture.get_size()`로 region을 계산하는데, **블릿이 실제로
  샘플하는 텍스처의 크기가 그 값과 다른 시점/조건이 존재**한다(풀스크린에서
  ViewportTexture 크기 보고 vs 실제 GPU 텍스처 불일치 또는 스테일). 정확한
  분기는 아래 계측이 확정한다 — **원격 추정으로 확정하지 말 것**.

**계측(수정과 함께 필수)**:
1. arm 시점과 post-draw 시점 각각에서 `window size · get_visible_rect().size ·
   root_texture.get_size() · region`을 로그로 남겨 4K 풀스크린 1회 재현.
2. 캡처된 380×375 프레임 1장을 PNG로 덤프해 깨짐 유무를 직접 확인.

**수정 계약**:
1. **선호 = 정규화 UV 크롭.** min-공식은 스케일 불변이므로
   (`u0 = (1 − s·Gx/Vx)/2`는 V를 캔버스로 넣든 프레임버퍼로 넣든 동일)
   **정규화 좌표로 표현하면 단위 혼동이 구조적으로 불가능**하다.
   `AtlasTexture.region`(절대 픽셀)을 버리고, TextureRect에 정규화 UV rect를
   받는 소형 셰이더(또는 동등 수단)로 교체하는 것을 우선 검토한다.
2. 절대 픽셀 region을 유지한다면: region은 **샘플러가 실제로 쓰는 크기**
   (`_blit_atlas.atlas.get_size()`를 그리는 시점에) 기준으로 계산하고,
   **하드 가드**를 건다 — `region ⊆ atlas 크기`가 아니면 캡처를 버리고
   폴백(**깨진 프레임이 링에 들어가는 것은 구조적으로 불가능해야 한다**).
3. 픽셀 QA 갭 보강: 비율 2.0 QA는 GREEN인데 실전 4K가 깨졌다 = QA가
   "region 계산 크기 ≠ 실제 샘플링 크기" 조건을 재현하지 못한다.
   **마커 기반 콘텐츠 단언**(캡처 프레임의 네 사분면 모두에 기대 콘텐츠 존재 —
   깨짐/공백이면 RED)을 **실 프로덕션 `_sync_blit_crop` + 실제 블릿 트리**를
   관통해 추가하고, 가능하면 창 크기 전환(리사이즈→캡처) 시나리오를 포함한다.
   ⚠️`sync_blit_crop_for_tests` 같은 테스트 심으로 우회하면 공허 GREEN이다.
4. 수정 후 **인게임 미감 재판정**(S1·S5, 4K 풀스크린 포함).

## 17. 해상도 상향 — 380×375 → 760×750 (2026-08-15)

### 17.0 경위 — 3차 인게임 판정

§16.9 후 3차 인게임 QA: **크롭 완전 정상**(전투 전체·양 액터·공 궤적·전광판,
잘림·깨짐 없음). 사용자 판정: *"이제 제대로 나오긴 하는데 화질이 너무 안좋아"* —
§16.6에 사전 등록된 세 번째 분기 그대로다: **RED가 아니라 해상도 안건.**
"녹화된 화면이 재생되는 느낌"의 골격은 성립했다.

원인은 산수다: 380×375는 폐기된 VRAM 링 시절(§12, 90MB VRAM 예산)의 유산인데,
4K 풀스크린에서 게임 영역은 ~2189×2160이라 **5.8배 업스케일**이 된다.
원본 핑파이터의 50% 캡처는 창 기준 2배 업스케일이었다 — 지금 비율이 원본보다
3배 가혹하다.

### 17.1 결정 — 760×750 (논리 캔버스 원본 해상도)

캡처를 **760×750 고정**으로 올린다. 근거:

- 이 게임의 아트는 760×750 논리 캔버스 기준으로 저작된다. 그 해상도로 캡처하면
  **아트가 가진 디테일 전부**가 담기고, 재생 업스케일(4K에서 2.88배)은 라이브
  게임 자신이 스프라이트에 하는 업스케일과 같은 급이 된다.
- 그 이상(프레임버퍼 동적 해상도)은 메모리가 GB급으로 뛰고, 아트 저작 해상도를
  넘는 픽셀은 수확이 급감한다. **760×750 초과는 이번 범위에서 제외.**

**예산 산수** (CPU RAM — VRAM 아님, §14 아키텍처 그대로):

```
프레임당 760×750×4 = 2,280,000B
링 60슬롯          = 136.8MB
클립 99프레임       =  225.7MB
논리 총합           = 159 × 2,280,000 = 362,520,000B  (≈362.5MB)
async 대역폭        = 2.28MB × 30Hz = 68.4MB/s (PCIe 대비 무시 가능)
블릿 뷰포트 VRAM    = 2.28MB
```

참고: 원본 투기장 하이라이트는 ~1.6GB CPU RAM을 썼다. 362MB는 그 1/4이다.
⚠️ 전시 PC 사양에서의 여유는 §16.4의 전시 출하 기본값 결정에 함께 얹는다.

### 17.2 변경 범위 (최소)

- `CAPTURE_SIZE` 380×375 → **760×750** (파생 상수 `CAPTURE_BYTE_COUNT` 자동).
- 블릿 뷰포트 크기 동반. **정규화 UV 크롭(§16.9)은 무변경** — 스케일 불변이라
  해상도와 무관하게 그대로 성립한다.
- 메모리 계약 상수: 논리 총합 90,630,000 → **362,520,000B**.
- 재생 `ImageTexture` 크기 동반. `update()` 대역 2.28MB×30fps=68.4MB/s —
  §14.9에서 570KB가 0.2~0.4ms였으므로 4배 데이터도 예산 내로 예상되나
  **실측으로 확인한다(가정 금지)**.

### 17.3 게이트 (기존 계약 승계 — 새 게이트 없음)

1. 픽셀 QA(§16.9의 실경로 관통 + 마커 사분면 + 리사이즈)를 **새 해상도로 재실행**.
2. 캡처·재생 프레임 마감 초과 0 · 드랍 0 (§14 형식 그대로 정보 출력.
   §14.9 수치를 크게 상회하면 자동 RED가 아니라 신규 발견 보고).
3. 메모리: 새 논리 총합 정확 일치 · 정리 시 전량 해제 · 소유 RID 0.
4. 헤드리스 로드 · 제품 구조 씰 GREEN 유지.
5. **인게임 4차 판정**(S1·S5, 4K 풀스크린): 화질 포함 최종 미감.

### 17.4 판정 분기

- **GREEN** → 승격 확정. B안 폐기. 커밋 정리(§16 파일들 + 본 변경 헝크 분리).
- **여전히 흐림** → 아트 저작 해상도 초과 캡처는 수확 급감이므로, 그때는
  해상도가 아니라 **재생 표시 방식**(필터·정수 배율 표시 등)을 별건 검토.
- **성능 신규 발견**(마감 초과 등) → §14.9 성질과 다른 신규 안건으로 보고 후
  사용자 판단.

## 18. 프레임률 상향 — 렌더 1:1 캡처·재생 (2026-08-15 사용자 확정 "B안")

### 18.0 결정

30fps 캡처·재생을 **렌더 프레임 1:1**(캡 72Hz)로 올린다. 사용자 선택.
§12~14의 "30FPS 고정"은 프로브 단계의 게이트 동결이었고, 이번은 §17과 같은
**사용자 승인 제품 사양 변경**이다 — 게이트 침식이 아니며 성능·메모리 게이트는
새 사양으로 재유도·재실측한다.

근거: ①라이브 72Hz vs 리플레이 30fps 격차 ②30은 72의 약수가 아니라 캡처
간격이 2~3프레임을 오가고 재생도 2~3틱 번갈아 표시되는 **저더**가 있었다.
1:1은 캡처·재생이 같은 세션 같은 렌더 루프이므로 **저더가 구조적으로 불가능**
하다. 원본 투기장(60fps)보다 부드럽고 메모리는 원본(1.6GB)의 절반 수준.

### 18.1 사양

- **캡처 = 매 렌더 프레임**, 상한 `MAX_CAPTURE_HZ = 72`(초과 렌더율에선 시간
  게이트로 72까지만 — 출하 기본 Stable 72라 실질 영향 없음, 90Hz+에선 상한
  구간 저더 잔존을 문서로 수용).
- 30Hz `CAPTURE_INTERVAL` 게이트는 제거(상한 게이트로 대체).
- **재생은 기존 타임스탬프 구동을 유지**한다. 렌더율이 캡처율과 같은 정상
  경로에서는 타임스탬프 선택이 자연히 1:1이 되고, 세션 중 렌더율이 바뀌는
  엣지에서도 스킵/반복으로 안전하게 흡수된다(슬로모션 금지).
- 수치는 **단일 정본**(상수에서 파생, §17 방식):

```
링   = 2.0s × 72        = 144 슬롯
클립 = 3 × floor(1.1×72) = 3 × 79 = 237 프레임
논리 총합 = (144+237) × 2,280,000 = 868,680,000B  (≈868.7MB CPU RAM)
async 대역 = 2.28MB × 72 ≈ 164MB/s
in-flight 정상 상태 ≈ 2 (2프레임 지연 × 매 프레임 요청) — 상한 재확인
```

### 18.2 게이트 (재유도·전부 실측)

1. **1:1 균일성 씰(신규 핵심)**: 동일 렌더율에서 99+ 프레임 재생 중 표시
   프레임당 캡처 프레임 전진이 정확히 1 — **반복 0 · 스킵 0**. 이것이
   "저더 구조적 불가"의 실측 봉인이다.
2. 지속 캡처: 매 프레임 요청 10초(720요청급) — due==produced · 드랍 0 ·
   마감 초과 0 · in-flight 고수위 기록.
3. 재생 업로드: 2.28MB × 72fps `update()` worst와 마감 실측(30fps의 0.62ms
   에서 부하 2.4배 — 예산 내 예상이나 **실측 확정, 가정 금지**).
4. 메모리: 새 논리 총합 정확 일치 · 정리 전량 해제 · RID 0.
5. 픽셀 QA(실경로·마커 사분면·리사이즈) 재실행 · 구조 씰 · 헤드리스 로드.
6. **5차 인게임 판정**(S1·S5, 4K 풀스크린): 부드러움 포함 최종 미감.

### 18.3 주의

- **868.7MB CPU RAM** — 개발기 무리 없음. ⚠️§16.4 전시 출하 기본값 결정에
  이 수치를 반드시 얹는다(전시 PC 사양 확인 전 기본 ON 출하 금지 성질 유지).
- 매치 리셋/전환/메뉴 복귀 해제 계약은 총량이 커진 만큼 더 중요 — 기존 씰 유지.
- 캡처 상한과 링/클립 슬롯 수가 전부 한 상수에서 파생되는지 확인(§17 정본화).

### 18.4 페이싱 계약 개정 — 프레임 재생은 timeline_speed = 1.0 (2026-08-15 승인)

**충돌 발견(Codex)**: 재생기가 선택 클립 합계를 **무조건 2.8~3.2초로 정규화**
한다(§5.1, 양식화 패널 시절 계약). 프레임 리플레이에 이걸 적용하면:
- 1클립(0.75~1.1초) 승리 → timeline_speed 0.27~0.39 → **캡처 프레임 2~4회
  반복(슬로모션)**
- 3클립(3.3초) → 3.2초 압축 → **스킵 필연**

즉 캡처만 72Hz로 올려도 실제 제품 경로에서 §18.2-1(반복 0·스킵 0)이 성립하지
않는다. 픽스처에서만 통과시키면 공허 씰이다. **발견이 씰의 목적 그 자체다.**

**개정**:

1. **프레임 클립이 하나라도 포함된 재생은 `timeline_speed = 1.0`**(혼합 재생
   포함 — 프레임/상태 클립이 섞여도 전 클립 자연 길이 재생. 클립별 속도 분기
   금지, 단일 재생에 두 시간축을 두지 않는다).
2. **순수 상태 폴백 재생은 기존 2.8~3.2초 정규화 유지** — 폴백 경로 무회귀.
3. 프레임 재생의 전체 길이는 자연 합계 **0.75~3.3초(+전환 0.12초×n)**가 된다.
   §5.1의 "전체 2.8~3.2초"는 **프레임 레인에 한해 이 절이 대체**한다.
   1클립 승리가 ~1.1초로 짧아지는 것은 수용 — 스킵 피로를 줄이는 방향이며,
   골 홀드 +0.25초가 여운을 담당한다. 체감 이슈는 5차 인게임 판정에서 확인.
4. **1:1 균일성 씰(§18.2-1)은 실 제품 재생 경로**(실 `playback_state` +
   timeline_speed 1.0)를 관통해야 한다. 픽스처 전용 통과는 무효.

## 19. 클립 길이 연장 — 시작 앵커 변경 + 골 홀드 (2026-08-15 확정 "A+C")

### 19.0 경위 — 5차 인게임 판정

화질·부드러움 GREEN, **"각 구간이 너무 짧다"**. 원인은 상한이 아니라 **시작
앵커**다: 클립 시작이 "마지막 플레이어 타격 −0.2초"라 마지막 타격이 골 직전이면
상한을 아무리 올려도 실제 영상은 짧다(`victory_highlight_recorder.gd:280`).
또한 현행 `MAX_CLIP_SEC`은 골 홀드를 **포함**하므로 총길이 산정에 홀드를 더해야
한다(`:294`). ⚠️"상한 조절 = 길이 조절"이라는 §18 논의 중의 전제는 오류였다.

### 19.1 계약

- **시작 앵커 변경**: 클립 시작 = `max(골 시각 − 1.5초, 링 oldest)`.
  **마지막 플레이어 타격은 시작 앵커에서 제외** — 표식·선별 지표로만 유지.
- **실공방 lookback = 1.5초** · **골 홀드 = 0.5초** · **총 클립 ≤ 2.0초**
  (홀드 포함).
- 홀드는 **마지막 GPU 프레임 표시 유지**(합성) — 추가 이미지 메모리 0.
- 수치 정본(72Hz · 760×750):

```
클립당 실공방 프레임 = floor(1.5 × 72) = 108
클립 프레임 = 3 × 108 = 324  ·  링 = 144 (불변)
논리 총합 = (144 + 324) × 2,280,000 = 1,067,040,000B  (≈1.07GB)
```

- 체감: 평범한 1클립 ≈ 2.0초(공방 1.5 + 홀드 0.5) · 3클립 최대 ≈ 6초 + 전환.

### 19.2 씰

1. **1:1 반복 0·스킵 0 씰은 1.5초 실공방 구간에 적용**한다(실 playback_state
   관통, §18.4 유지).
2. **홀드는 별도 씰로 분리**: 마지막 프레임 표시 유지 시간이 0.5초(허용 오차
   명시)이고 그 구간에 프레임 전진이 없음을 단언.
3. 메모리: 새 논리 총합 1,067,040,000B 정확 일치 · 정리 전량 해제 · RID 0.
4. 시작 앵커: 골 −1.5초보다 링이 짧은 경우(이른 골) 링 oldest에서 시작하고
   실패하지 않음.
5. 픽셀 QA·구조 씰·헤드리스 승계.
6. **6차 인게임 판정**(S1·S5 4K): 길이 체감 최종.

### 19.3 확장 예약 (이번 범위 아님)

그래도 짧으면 **lookback만 2.0초로** 올린다(= B+C: 총 클립 2.5초 · 3클립
~7.5초 · 1,313MB — 링 2.0초 전체 사용이라 링 확장 불필요). 그 이상은 링
확장이 필요하므로 별도 계약.

## 20. 풀캔버스 재생 — 프레임 리플레이 표시 크기 변경 (2026-08-15 승인)

### 20.0 경위 — 6차 인게임 판정

길이 GREEN("좋은데"). 신규 요청: *"실제 게임화면과 동일한 사이즈 풀화면에서
그대로 재생"*. 현행 표시는 §11 양식화 패널의 유산(콘텐츠 밴드 y=118~678에
축소 표시)이다. 캡처는 이미 **게임 캔버스 전체(760×750·HUD 포함)**이므로
풀사이즈 표시가 곧 "게임이 그 자리에서 다시 재생되는" 원본의 형태다.

### 20.1 계약

- **프레임 클립 재생의 dest = 게임 캔버스 전체**(논리 0,0,760,750 · 1:1).
  밴드 변환·축소 없음. 4K에서 업스케일 2.88배 = 라이브 게임 자신과 동일.
- **오버레이 크롬은 콘텐츠 위에 얹는다**: 제목("승리의 순간")·부제 라벨·클립
  인디케이터 점·스킵 안내를 캡처 화면 위 오버레이로. 가독성은 **텍스트 뒤
  국소 스크림(저알파 띠) 또는 아웃라인**으로 확보 — 전면 어둡게 깔기 금지
  (리플레이가 어두워지면 목적 훼손).
- **순수 상태 폴백 재생은 기존 밴드 패널 유지**(무회귀 — §18.4와 같은 레인
  분리).
- 혼합 재생(프레임+상태 클립): 프레임 클립은 풀캔버스, 상태 클립은 기존 밴드
  — 클립 전환 시 표시 모드도 전환(교차 페이드가 흡수).
- 플레이필드 클립 호스트(§5.3, 760×750 `clip_contents`)는 유지 — 풀캔버스
  dest가 곧 클립 rect라 레터박스 누출 불가 구조 유지.
- 레터박스 필러의 라이브 크롬은 그대로 둔다(리플레이 밖 액자 역할 —
  전리품 페이즈와 동일 성질).

### 20.2 씰 충돌 재조정 (사전 명시)

⚠️ **기존 "콘텐츠가 제목·부제·스킵 대역 밖" 픽셀 씰(§11·§16.5-7)은 풀캔버스
재생과 설계상 양립 불가**다(콘텐츠가 캔버스 전체를 채우는 것이 목적).
- 그 씰의 스코프를 **상태 레인 전용으로 재조정**한다(삭제 아님 — 상태 패널은
  여전히 그 계약을 지킨다).
- 프레임 레인 신규 씰: ①dest가 정확히 풀캔버스(코너 마커가 캔버스 코너에
  1:1 도달, 픽셀) ②오버레이 텍스트가 실제로 그려짐 + 국소 스크림/아웃라인
  존재 ③레터박스 누출 0 재확인.

### 20.3 씰

1. 프레임 재생 dest = 풀캔버스 픽셀 씰(코너 1:1).
2. 1:1 균일성·홀드 씰(§19) — 표시 크기 변경에 불변임을 재실행으로 확인.
3. 상태 폴백 = 기존 밴드 + 기존 대역 씰 유지(레인 스코프 재조정 후 GREEN).
4. 혼합 재생 전환 레그(프레임 풀캔버스 ↔ 상태 밴드).
5. 픽셀 QA·구조 씰·헤드리스 승계.
6. **7차 인게임 판정**: 풀화면 체감 최종.

### 20.4 비용

표시 크기만 변경 — 캡처·메모리·업로드 불변(같은 텍스처를 더 크게 그릴 뿐).
성능 게이트 재측정 불요, 픽셀 QA 재실행으로 충분.

## 21. 홀드 스킵 — 길게 눌러 건너뛰기 (2026-08-15 승인)

### 21.0 결정

스킵 트리거를 **단발 클릭/키 → 길게 누르기(홀드)**로 변경하고, 재생 중 안내
문구와 홀드 진행 표시를 띄운다. 부수 효과: 득점 순간 잔여 입력의 오발 스킵을
구조적으로 제거한다(기존 0.15초 진입 무시창의 상위 호환).

### 21.1 계약

- **트리거**: 마우스 버튼 또는 키보드 키를 `SKIP_HOLD_SEC := 0.6` 이상 누르고
  있으면 전체 하이라이트 스킵. 임계 전에 떼면 스킵 없음 + 진행 리셋.
  기존 스킵이 받던 입력 종류를 그대로 승계(패드 버튼 포함 여부도 기존과 동일).
- **F9는 계속 통과**(§5.4 계약 유지 — 홀드 대상 아님).
- **안내 문구**: `victory_highlight_skip_hint`를 홀드 안내로 교체
  (예: "길게 눌러 건너뛰기"). ⚠️**7개 언어 락스텝** · 한국어 카피 엠대시 금지.
- **홀드 진행 표시**: 누르는 동안 문구 부근에 진행 게이지(0→1 채움).
  팔레트는 기존 chrome 모듈 링크 참조(`BRASS_LIGHT` 계열), ⚠️얇은 외곽선
  스트로크 금지(레포 VFX 규칙) — 채움/글로우로. 떼면 게이지 리셋.
- **양 레인 공통**: 프레임 풀캔버스·상태 밴드 모두 동일 메커니즘
  (`playback_state` 입력 처리 한 곳 소유 — 레인별 복제 금지).
- 클립 경계를 넘는 홀드는 계속 누적(전역 타이머).
- 진입 직후 무시창은 **누름 시작 시각**에만 적용(유지 가능·홀드가 사실상 흡수).

### 21.2 씰

1. 홀드 < 0.6s 후 릴리스 → **스킵 없음** + 진행 리셋.
2. 홀드 ≥ 0.6s → 전체 스킵 → 종료 콜백 → 상자 드랍 진행.
3. **단발 클릭이 더 이상 스킵하지 않음**(구 동작 반증 레그 — 기존 씰 중
   "1회 입력 = 전체 스킵" 단언은 이 절로 대체).
4. 게이지·문구가 실제로 그려짐(픽셀).
5. 문구 7개 언어 락스텝.
6. F9 통과 유지.
7. **8차 인게임 판정**: 홀드 체감·문구 가독.

## 22. 오버레이 정리 — 프레임 잔재 제거 + 자동 페이드 (2026-08-16 확정)

### 22.0 경위

8차 인게임 QA: 풀캔버스·불투명 바닥·홀드 안내 전부 계약대로. 발견 1건 —
`_draw_clip_overlay`(`victory_highlight_renderer.gd:136`)가 구 양식화 패널의
`_draw_frame`(황동 테두리 + y=118/678 밴드 라인)을 **프레임 레인에서도** 호출.
§20.1 오버레이 목록(제목·부제·점·스킵)에 없는 계약 밖 요소로, 풀화면인데
"패널 안" 인상을 남긴다. 추가로 사용자 결정: **풀캔버스 영상이 주역** —
제목·부제는 자동 페이드.

### 22.1 계약 (프레임 레인)

- **구 황동 프레임·밴드 라인 제거** — 프레임 레인 오버레이에서 `_draw_frame`
  호출 제외.
- **제목("승리의 순간")**: 재생 시작 후 **0.8초 유지 → 0.25초 페이드**,
  이후 재등장 없음(클립이 바뀌어도).
- **부제(클립 라벨, 예: "결정타")**: **각 클립 전환마다 0.6초 표시 → 0.2초
  페이드**(클립 종류 전달은 유지하되 장면을 오래 가리지 않음).
- **클립 인디케이터 점 · 홀드 스킵 안내 · 홀드 게이지는 상시 유지.**
- 텍스트 표시 중의 국소 스크림은 텍스트와 함께 페이드(§20.1 가독 규칙 유지).

### 22.2 상태 폴백 레인

**기존 표시 그대로 유지**(황동 프레임·밴드 라인·상시 제목 포함) — 무회귀.

### 22.3 씰

1. 프레임 레인: 황동 프레임·밴드 라인 픽셀 **부재**(제거 반증 — 있으면 RED).
2. 제목 타임라인: 0.8s 유지 → 0.25s 페이드 → 재등장 없음(클립 전환 후에도).
3. 부제 타임라인: 클립 전환마다 0.6s → 0.2s 페이드.
4. 점·스킵 안내·게이지 상시 표시 유지.
5. 상태 레인: 기존 오버레이 픽셀 씰 그대로 GREEN.
6. **9차 인게임 판정**: 페이드 체감 최종.
